## 2. 공개 함수

```js
import {runCare} from './engine/index.mjs';

const out = await runCare(payload, {signal, deadlineAt, consent, requestId}, deps);
// out = {response, trace}            정상
// out = {response: null, error, trace} 오류·취소 → 서버는 오류로 응답(프론트가 재시도 UI)
```

- `payload`: 프론트 요청 그대로(`reason`, `locale`, `messages`, `followUpAnswers`, `profile`, `search`, `intake`, `previousReport`).
- `response`: **프론트 계약 객체만**(`followUp` | `summary` | `search` | `emergency` | `profileUpdates`). 엔진의 계약 검사(§8)를 통과한 것만 내보낸다. 통과 못 하면 `error:'contract'`.
- `trace`: 팀원 3 서버용 구조 정보. **사용자 원문을 넣지 않는다.**
  `{engineVersion, dataVersion, questionnaireVersion, reason, phase, ruleHits:[rule_id], terminal, nextQuestionId, symptom:{id, source, fallback, fallbackGroup}, slots:{card, filter, detail, report, flow}, skippedItems, llm:{classify, profile}, warnings}`
  - `slots.card`는 119 신고 요약 카드(팀원 3)용, `slots.filter`는 진료과 필터.
  - *(11/16 E 반영)* 구현에서 더한 필드: `templateVersion`, `freeTextVersion`, `facilityKeywordsVersion`. `llm.classify`는 상태·사유·의도·provider·후보 수만(원문·지연 시간 없음, 같은 입력이면 같은 trace), `llm.profile`은 `{called, itemCount, fields, error}`.
- `deps`(테스트·교체용): `{refStore, matchSymptoms, llm:{classifySymptom, extractProfileUpdates}, freeTextRules, log, now}`.
  - *(11/16 E 반영)* `facilityKeywords`(키워드 규칙 객체)도 받는다. `refStore`는 `loadIntakeData()`와 같은 형식의 객체 또는 그것을 돌려주는 함수.
- **예외를 밖으로 던지지 않는다.** 시간: `deadlineAt`과 `now + 7000ms` 중 이른 쪽. LLM 호출은 요청당 최대 1번.
  - *(11/17 EF 반영, 독립 검토 G1)* 주입 함수 호출을 모두 감싼다: `deps.now`가 던지거나 숫자가 아니면 `Date.now()`, `deps.log`가 던지면 무시(LLM 모듈에 넘기는 log도 같은 감싼 함수), deps·ctx 필드를 읽다가 getter가 던져도 없는 값으로 본다. 그 밖의 실패는 지금처럼 `data`·`internal` 오류 코드로 돌아온다.
- *(11/16 E 반영)* 오류 코드: `unsupported_reason`, `aborted`, `data`(데이터·규칙 파일 로드·검사 실패), `contract`(응답이 계약 검사 실패), `internal`(그 밖 예외).

## 3. 데이터 (`engine/intake-data.mjs`)

- 읽는 파일(시드, 읽기만): `questionnaire*.csv`, `safety_rule*.csv`, `output_mapping.csv`, `item_topic.csv`, `symptom.csv`, `symptom_department.csv`, `symptom_department_variant.csv`, `department.csv`, `fallback_department.csv`, `app_config.csv`, `data_version.csv`. CSV 파서는 `llm/ref-data.mjs`의 `parseCsv`를 쓴다.
- `data_version` 하나로 고정(다르면 그 행 제외 + 경고, LLM 모듈과 같은 규칙).
- **로드 때 검사**(실패하면 로드 실패): 링크 ID·선택지 code 형식, 선택지 0~12개(todo 문항만 0개 허용), order 중복 없음, enableWhen이 자기보다 앞 문항만 가리킴, 지원하지 않는 operator 없음, 안전 규칙 조건이 가리키는 문항·code 존재, `answers` 비어 있지 않음, 결과 매핑 slot 형식, 추천에 쓰이는 진료과의 `search_key`가 비어 있지 않음.
- 나중에 Supabase 로더를 같은 반환 형식으로 추가한다(`refStore.source = 'csv' | 'supabase'`).
- *(11/16 E 반영)* 구현한 검사에서 바뀌거나 더한 것: 선택지 0개는 todo 문항과 **선택지가 없는 형식(string·display)**에도 허용(N4 등 string 문항은 원래 선택지가 없다), string 문항에 선택지가 있으면 거부. 안전 규칙 `priority`는 10 이상 정수·중복 없음(1~9는 자유 입력 규칙 예약, §7), `=` 조건은 answers 1개. `engine_condition`은 빈 값·`symptom_is_fallback`만, `ui`는 빈 값·`frontend`만. `report.symptom` 매핑은 정확히 1개(이 매핑이 가리키는 문항 = 증상 확인 자리, 코드에 N4를 박지 않으려고). `fallback_department`에 `general`·`injury` 그룹 필수.

## 4. 처리 순서 (매 요청)

> *(11/16 오후 수정)* 근거 조사(ChatGPT 교차 검토)와 사실 확인(`docs/reports/engine_precheck.md`)을 반영해 **증상 확인을 안전·대상 질문 뒤로 옮겼다.** 처음 안의 근거 "상태가 없어서 LLM 결과를 미룰 수 없다"는 틀렸다. 메시지는 매 요청 다시 오므로, 증상 확인 차례에 LLM을 부르면 된다.

```
0. 입력 정리     ── reason 확인, 답 정리(§4-5)
1. 안전 규칙     ── 자유 입력 규칙(메시지) + 답 규칙(보이는 답)  → 걸리면 §6 응급 처리
2. 시작 선택     ── 엔진 질문(ASK_START, MED_CHOICE)의 답이 있으면 그대로 처리(§4-4)
3. 키워드 기관 찾기 ── 첫 요청에서만 의미 있음. 조건이 맞으면 search만 돌려줌(§4-6, LLM 없음)
4. 다음 문항     ── Q0 → N1~N3 → T1~T3 (데이터 order 그대로)
5. 증상 확인     ── T1~T3 다음(N4 자리). 사전 → LLM → 확인 질문(§4-2)
6. 다음 문항     ── 상세(N5~N13, P0·P1, 조건부 F2)
7. 완료          ── 남은 문항이 없거나 reason=skip → 추천·요약·검색 조건·건강정보 후보(§8)
```

- 안전 질문과 대상 질문 동안에는 LLM을 부르지 않는다. 증상 확인 단계에서 LLM을 부를 때 T2(성별)를 이미 알므로 후보도 더 정확해진다.
- Q0=예이면 증상 확인까지 가지 않는다(T1~T3도 Q0=아니요 조건). 응급 흐름만 진행한다.
- **[근거]** 생명 위협 확인을 먼저 하는 순서: NHS Pathways는 생명을 위협하는 상황을 통화 초기에 확인하고, KTAS는 첫인상 위험도 평가 뒤 주호소를 본다(ChatGPT 교차 검토 결과, 출처는 그 보고서). 두 화면 순서를 직접 비교한 연구는 확인 못함.
- 질문 수(사실 확인 §8): 증상 사용자는 결과까지 19~24문항, 증상 확인 직후 '여기까지 답하고 찾기'를 누르면 8문항. 약국 키워드 사용자는 0문항.
- *(11/17 EF 반영)* 2단계(시작 선택)는 메시지에 사전 증상 매칭·증상 단서·위험 단서가 있으면 검색 답을 무시한다(§4-4). 3단계(키워드)는 **약국 찾기 문장만** 바로 search로 보내고 위험 단서가 있으면 막는다(§4-6 v2). 병원·진료과 찾기 문장은 0문항 → 7문항(Q0~T3 뒤 LLM 의도 `facility_search`).

### 4-1. 안전 규칙 (맨 먼저)
- 답 규칙: `ref.safety_rule` + `safety_rule_condition`. 조건이 가리키는 문항이 **보이지 않으면 그 조건은 거짓**(숨겨진 문항의 답은 계산에서 뺀다).
- 자유 입력 규칙: `engine/rules/free_text_v1.json`(v1은 `rules: []`). 형식은 §7. `messages` 전체를 정규화해서 본다.
- 결과 고르기(priority hit policy): 걸린 규칙 중 `priority`가 가장 작은 것. 걸린 규칙 ID는 모두 `trace.ruleHits`.
- 시작 선택(약국 찾기 등)을 골라도 이미 걸린 위험 규칙은 풀리지 않는다(1단계가 항상 먼저).

### 4-2. 증상 확인 (T1~T3 다음, 상태 없이)

| 순서 | 조건 | 할 일 |
|---|---|---|
| a | `SYM_CONFIRM`(LLM 후보 확인) 답이 있음 | `parseSymptomConfirm`: 증상 ID면 확정(source `llm_confirm`), `sym_none`·`sym_unsure`·이상한 값이면 증상 모름. **LLM 다시 안 부름** |
| b | `SYM_DICT_CONFIRM`(사전 후보 확인) 답이 있음 | 증상 ID면 확정(source `dict_confirm`). `sym_other`(다른 증상이에요)면 **LLM을 한 번 부른다**(→ c의 결과). `sym_unsure`·이상한 값이면 증상 모름 |
| c | `SYM_NOT_FOUND` 답이 있음 | 증상 모름으로 확정. LLM 다시 안 부름 |
| d | 메시지가 없음 | `ASK_START` 질문(§4-4) |
| e | 사전 매칭 1개 이상 | `SYM_DICT_CONFIRM` 질문(사전 후보 최대 5개 + `sym_other` + `sym_unsure`). LLM 안 부름 |
| f | 사전 매칭 0개 | `classifySymptom`: `confirm` → 그 followUp(`SYM_CONFIRM`) 그대로 / `fallback` → `SYM_NOT_FOUND` / `route` → §4-4 |

- *(11/17 EF 반영, 독립 검토 I1)* **답이 있는 엔진 질문은 나중에 나오는 질문부터 본다: a(`SYM_CONFIRM`) → c(`SYM_NOT_FOUND`) → b(`SYM_DICT_CONFIRM`).** 이전 순서(a → b → c)에서는 `sym_other` → LLM 실패 → `SYM_NOT_FOUND`에 답해도 b가 먼저 걸려 같은 질문과 LLM 호출이 요청마다 반복됐다. 이제 `SYM_NOT_FOUND` 답이 있으면 `sym_other`가 있어도 증상 모름, `SYM_CONFIRM` 답이 있으면 그 결과이고 둘 다 LLM을 다시 부르지 않는다. `SYM_DICT_CONFIRM`=`sym_other`만 있을 때 LLM 1번. 테스트: 엔진 질문 답 조합 75가지 × LLM 결과 5종 × 메시지 2종(`ef-i1.test.mjs`).

- **사전이 일부만 맞은 경우를 위한 `sym_other`** *(11/16 오후 추가)*: 사실 확인에서 c24(응급 사례)는 사전이 부수 증상(A09 땀)만 맞혀 LLM이 불리지 않았고, 확인 질문에 정답(A11 가슴 통증)이 없었다. 사전 확인 질문에 "다른 증상이에요"를 두고, 고르면 그때 LLM을 부른다. 사전이 맞힌 원문은 사용자가 고르기 전까지 외부로 나가지 않는다(LLM 설계 §0-1 유지).
- **[판단] 사전 매칭도 확인 질문을 거친다**(유지, 교차 검토 권고와 같음). 일치 개수는 부정·시점·대상까지 맞게 읽었다는 증거가 아니다.
- **[판단] v1은 부정 규칙을 넣지 않는다.** 사실 확인에서 "뒤 3글자 안의 없·안·않·아니" 규칙은 draft_v0에서 뺀 매칭이 0개였고, 직접 만든 "안 멈춰요"류 양성 문장 3개를 모두 잘못 뺐다. 오매칭은 확인 질문의 `sym_other`·`sym_unsure`로 사용자가 바로잡는다. 평가셋에 부정문("A는 없고 B")과 계속됨을 뜻하는 양성 문장("안 멈춰요")을 넣어 측정한 뒤 다시 정한다. 교차 검토는 부정 처리를 함께 하라고 권했다 — 이 차이는 §11에 남긴다.
- **[판단] LLM 실패도 질문(`SYM_NOT_FOUND`)으로 남긴다.** 답으로 남기지 않으면 다음 요청마다 LLM을 다시 부르고, 중간에 결과가 바뀔 수 있다.
- 분류할 텍스트: 사용자 메시지 전체를 줄바꿈으로 이은 것(LLM 모듈이 PII를 가리고 끝 500자만 보낸다). `sex`는 T2가 female/male이면 그 값.
- 증상이 정해진 뒤 들어온 새 메시지는 증상 확인에 다시 쓰지 않는다(v1). 안전 규칙에는 매번 쓴다.
- 사전 매칭 함수 `matchSymptoms(text, refData, {sex}) → symptomId[]`(관련도 순)은 `deps`로 교체할 수 있다. 기본 구현: 정규화한 입력 안에 동의어 `term_norm`이 들어 있는지 보는 포함 검사, 한 글자 표현은 바로 뒤가 이·가·을·를일 때만, fallback·상위 증상과 성별이 맞지 않는 증상 제외, 맞은 표현 길이 내림차순. **팀원 2의 사전 매칭 모듈이 오면 교체한다.**

### 4-3. 다음 문항
`order` 오름차순으로 처음 만나는 "물을 문항" 하나. 아래는 **묻지 않는다.**

| 건너뛰는 문항 | 이유 |
|---|---|
| `todo: true` (N6-2, N9-1, N10-1, P2, P3, F1) | 선택지 미정(D5 결정) |
| `ui: frontend` (E3) | 프론트 응급 모달의 위치 기능이 처리 |
| `type: string` (N4, N8-1, N11-1, N13-1, F3) | 프론트는 서버 질문을 `singleChoice`로만 받는다(사실 확인 §1: `frontend/intake-data.mjs:13-19`). 자유 입력은 `messages`로만 오고 어느 질문의 답인지 표시되지 않는다. N4는 증상 확인(§4-2)이 대신한다 |
| `engine_condition: symptom_is_fallback` (F2) | 증상이 fallback 증상이거나 모를 때만 묻는다 |
| 응급 종료 중 | `flow: emergency` 문항만 묻는다(§6) |

- 이미 유효한 답이 있는 문항, enableWhen이 거짓인 문항도 건너뛴다.
- 실제로 묻는 순서: Q0 → (Q0=예) E1, E2, E4~E9-1 / (Q0=아니요) N1~N3 → T1~T3 → **증상 확인** → N5~N13 → P0·P1 → (조건부) F2.
- 증상 확인은 데이터 문항이 아니므로, 엔진은 "N4 자리"(T3 다음, N5 앞)에서 §4-2를 끼워 넣는다. 위치는 N4의 `order`로 정한다(N4보다 order가 작은 물을 문항이 남아 있으면 그것이 먼저).
  - *(11/16 E 반영)* N4가 보일 때(Q0=아니요)만 이 자리가 열린다. N4 뒤 문항에 이미 답이 있어도 증상이 정해지지 않았으면 증상 확인이 먼저다. `nextQuestion`은 `{kind:'item'|'identify'|'done', item?, skippedItems}`를 돌려준다(지시서의 "item 또는 null"을 객체로 바꿈).
- 문항 → followUp: `id = link_id`, `type: 'singleChoice'`, `required = item.required`, `label = {ko: text_ko, en?: text_en}`, `options = [{id: code, label: {ko: display_ko, en?}}]`.
- **string 문항 4개의 정보**(이전과 다른 점, 약·처치, 기존 질환, 동반 증상)는 교차 검토 권고대로 **선택형 문항으로 바꿔 수집한다 — 데이터 작업**(`intake_v1.yaml`, todo 문항과 같은 묶음: 근거 조사 → 선택지 → 검토). 문항이 선택형으로 바뀌면 엔진 코드는 고치지 않아도 자동으로 묻는다. v1 요약에는 "확인하지 않은 정보"를 적는다(§8-2).

### 4-4. 엔진 질문 (데이터가 아닌 질문 5개, 문구는 `engine/templates.mjs`)
| ID | 언제 | 선택지 | 답의 처리 |
|---|---|---|---|
| `SYM_DICT_CONFIRM` | 사전 후보가 있을 때 | `sym_<id>` 최대 5개 + `sym_other`(다른 증상이에요) + `sym_unsure`(잘 모르겠어요) | §4-2 b |
| `SYM_CONFIRM` | LLM 후보가 있을 때 | `sym_<id>` + `sym_none` + `sym_unsure` | LLM 모듈 그대로(§4-2 a) |
| `SYM_NOT_FOUND` | LLM fallback(시간 초과·오류·후보 없음·동의 없음) | `sym_continue`(질문에 답할게요) | 증상 모름 → 문진 계속 |
| `ASK_START` | 메시지 없음, 또는 LLM 의도 `other` | `find_hospital`, `find_pharmacy` | 검색 조건만 돌려줌 |
| `MED_CHOICE` | LLM 의도 `medication_question` | `med_symptom`(증상·부작용 상담), `med_pharmacy`(약국 위치 찾기), `med_info`(복용법 등 약 정보 문의) | 증상·부작용 → 증상 모름으로 문진 계속 / 약국 → 검색 / 약 정보 → 안내 요약 + 약국 검색 |

- LLM 의도 `facility_search`(키워드 규칙에 안 걸린 기관 찾기)는 질문 없이 search만 돌려준다. search 만드는 법은 §4-6과 같다.
- **[판단] 약 질문은 사용자가 다시 고른다**(유지). 버튼 문구는 교차 검토 권고대로 뜻을 분명히 했다. 약 의도는 증상 확인 단계에서야 알 수 있어서 약 의도 사용자도 안전·대상 질문 7개를 먼저 답한다. 교차 검토의 "위험 평가가 의도 재확인보다 먼저"와 맞고, 약 질문에는 부작용·과량 복용이 섞일 수 있어서 이 순서를 받아들인다(사실 확인 §8: 8문항).
- 시작 선택(`ASK_START`, `MED_CHOICE`)의 답이 있으면 증상 확인보다 먼저 처리한다(사용자가 명시적으로 고른 것).
- *(11/17 EF 반영, 독립 검토 G3)* **시작 선택 고정 해제**: 메시지에 사전 증상 매칭·`symptomCues`·`riskCues`(§4-6 v2) 중 하나라도 있으면 검색 답(`find_hospital`, `find_pharmacy`, `med_pharmacy`, `med_info`)을 무시하고 정상 흐름으로 간다(warning `start_choice_overridden`, 값 없음). `med_symptom`은 기존대로(증상 모름으로 문진 계속). *[판단]* 이렇게 정상 흐름으로 온 요청의 증상 확인은 **LLM을 부르지 않는다**: 사전 매칭이 있으면 `SYM_DICT_CONFIRM`, 없거나 `sym_other`면 증상 모름(source `start_choice`). LLM을 다시 부르면 같은 시작 질문(`ASK_START`·`MED_CHOICE`)이 다시 나오거나 경로 전체 LLM 호출이 2번이 된다.

### 4-5. 답 정리
- `followUpAnswers`에서 같은 `questionId`는 마지막 것만.
- 값이 null·undefined → 미응답. 그 문항에 없는 code → 미응답 + `trace.warnings`(값은 남기지 않음).
- 미응답·모름(`unknown`)·아니요(`no`)·건너뜀(reason=skip 때 남은 문항)을 구분한다. 미응답을 `no`로 바꾸지 않는다.
- 보이지 않는 문항의 답은 계산·매핑에서 뺀다.

### 4-6. 키워드 기관 찾기 *(11/16 오후 추가)*

  4. **증상 단서가 없음**: `아프|아파|아픈|통증|쑤시|저리|붓|부었|열이|열나|토하|토할|구토|어지러|기침|피가|피나|다쳤|다친|숨이|숨쉬|가려|따가|메스꺼` — *[판단]* 사실 확인 §5가 지적한 "배가 아픈데 문 연 병원" 같은 문장이 문진 없이 진료과 없는 검색으로 가지 않게 한다. 이런 문장은 안전 질문부터 거친다.
  5. **약 질문 단서가 없음**: `복용|먹어도|먹으면|부작용|같이먹|함께먹|용량|몇알|몇번먹|약을먹|약먹` — BACKEND.md 0.20.0(361행) "약 질문을 일반 약국 검색과 동일하게 처리하지 않습니다". 이런 문장은 LLM 의도 → `MED_CHOICE`로 간다.
- 응답 search: `약국`이 있으면 `{type:'pharmacy', department:'pharmacy'}`, 아니면 `{type:'hospital'}`. 진료과 이름이 있으면 그 과의 `search_key`를 `department`로(옛 이름은 표로 연결). `문연|영업중|운영중|열려있|연곳|여는|열린|진료하는`이 있으면 `openOnly: true`.
- 단서 목록은 초안이다. 평가셋에서 오탐·누락을 재고 고친다(파일 버전 `facility-keywords-v1`).
- *(11/16 E 반영)* 구현에서 정한 것: (1) 이름은 더 긴 이름을 먼저 본다('정형외과' 안의 '외과'를 따로 세지 않음). (2) 증상·약 단서는 **기관·진료과 이름을 지운 뒤** 본다('마취통증의학과'의 '통증'이 단서로 걸리지 않게). (3) `never_recommend` 과(응급의학과) 이름이 있으면 바로 search로 보내지 않고 안전 질문부터 거친다. (4) '약국' 판정 패턴은 규칙 파일의 `pharmacyPatterns`. (5) 메시지마다 따로 본다(요청어 6글자 창이 메시지 경계를 넘지 않음). 옛 이름 '한의원'은 프론트 key `korean`.

## 5. 결과 매핑
`output_mapping`을 보이는 답에 적용해 `trace.slots`를 채운다. `when`이 `any`면 답 code(또는 `value`)를 넣는다. 규칙 매핑은 걸린 규칙에만.
- `filter.sex`: T2 → female / male / unknown(`not_specified`·`unknown`·미응답).
- `filter.age_band`: T3 → child / adult / unknown(미응답 포함).
- `report.symptom`: 확정 증상의 `name_ko`(원문 아님). 모르면 비움.
- `profile.age`(내 정보의 만 나이)는 v1에서 쓰지 않는다. **[판단]** 상담 대상이 본인이 아닐 수 있다(T1).
- *(11/17 EF 반영, G4)* 사전 매칭·LLM에 넘기는 성별도 **보이는 답**(visibleCodes)의 `filter.sex` 매핑에서만 읽는다(숨겨진 T2 답은 쓰지 않는다).

## 6. 응급 처리

| 결과 | 응답 | 이후 |
|---|---|---|
| `EMERGENCY_STOP` (Q0=예, 자유 입력 규칙) | `emergency:{active:true, title, message}` + 다음 `flow: emergency` 문항(있으면) | E 문항은 119 신고 카드용, 답하지 않아도 됨. 다 끝나면 `emergency` + `summary`(119에 알릴 내용 정리, 정리할 답이 없으면 생략). 자유 입력 규칙으로 걸리고 Q0가 '예'가 아니면 E 문항이 보이지 않으므로 `emergency`만. **진료과 추천·search 금지** |
| `URGENT_NOTICE`, `terminal: true` (N1·N2·N3) | `emergency:{active:true, title, message}`만 | 더 묻지 않음. 진료과 추천·search 금지 |
| `URGENT_NOTICE`, `terminal: false` (지금은 없음) | `emergency` + 문진 계속 | 추천 가능 |

- *(11/17 EF 반영, G2)* `emergency_call_119` 문구 끝에 "이 서비스는 진단을 하지 않아요."를 붙였다(URGENT 문구와 같게). search만 있는 응답(약국 지름길, LLM `facility_search`, 시작 선택 검색)은 문장 필드가 없으므로 바꾸지 않는다 — summary를 붙이면 분석서에 들어가기 때문(119 안내를 붙일지는 §11).
- 안내 문구는 `message_key`별 템플릿(초안, `review_status: draft`). title ≤ 120자, message ≤ 1000자. `topicId`·`videos`·`instructions`는 넣지 않는다(검토된 응급처치 항목 선택은 팀원 3, 프론트 0.23.0이 등록된 가이드만 보여 줌).
- *(11/16 E 반영)* `EMERGENCY_STOP` 중 `reason=skip`이면 남은 E 문항을 묻지 않고 `emergency` + 119 정리 요약(정리할 답이 없으면 `emergency`만). `result`가 `EMERGENCY_STOP`이면 `terminal` 값과 상관없이 멈춘다(보수적).
- **사용자가 안전 답을 고치면**(프론트가 그 뒤 답을 지움) 규칙이 다시 계산된다. 상태가 없으므로 고친 답을 따른다. 응급 표시를 계속 둘지는 화면(프론트·팀원 3) 정책 — 보고서에 적는다.

## 7. 자유 입력 위험 표현 규칙 (자리만)

`engine/rules/free_text_v1.json`
```json
{
  "version": "free-text-v1",
  "rules": [
    {"rule_id": "FT-...", "priority": 5, "patterns": ["정규식 문자열"], "result": "EMERGENCY_STOP",
     "terminal": true, "triage_category_id": 17, "message_key": "...",
     "evidence": {"source": "manual_119", "page": 0, "note": "..."}, "review_status": "draft"}
  ]
}
```
- 패턴은 정규화한 메시지(NFKC → 소문자 → 공백 제거, LLM 모듈 `normalize.mjs`)에 적용. 부정문 처리는 다음 작업에서 정한다.
- 답 규칙과 같은 결정표에 넣어 priority로 고른다. `priority`는 답 규칙과 겹치지 않게(1~9 예약).
- 걸린 원문·패턴 위치는 로그·trace에 넣지 않는다(rule_id만).
- v1 테스트는 테스트 전용 규칙 파일로 배관만 확인한다.

## 8. 완료 처리

### 8-1. 진료과 추천
| 경우 | 추천 |
|---|---|
| 증상 확정, fallback 아님 | `symptom_department_variant`에서 (증상, `filter.sex`, `filter.age_band`) 행을 rank 순으로 최대 `max_recommendations`(3)개. DB 함수 `ref.recommend_departments`와 같은 결과 |
| 증상이 fallback 증상 | `fallback_department`의 그룹: 증상 `is_injury` 또는 F2=예 → `injury` / 증상 `fallback_group = pediatric` → `pediatric` / 그 밖 → `general` |
| 증상 모름 | F2=예 → `injury`, 그 밖 → `general` |

- `search = {type:'hospital', department: <1순위 search_key>}`. 나머지 과는 요약에 적는다.
- `never_recommend`(응급의학과)는 넣지 않는다(데이터에 이미 반영, 엔진에서 한 번 더 거른다).
- *(11/16 E 반영)* fallback 목록에도 진료과의 대상 조건(`sex_only`, `max_age`)을 적용한다: 성인(adult)에게 소아청소년과를 빼고, 그 결과 그룹이 비면 `general`. 확정 증상이라도 (증상, 성별, 나이대) variant 행이 없으면 DB 함수처럼 fallback으로 간다. F2(다쳐서 생긴 증상)는 결과 매핑 slot이 없어 ID로 읽는다(T1과 같은 예외).
- *(11/16 E 반영, 데이터 사실)* 여성 제한 증상(W·X 장)의 `male` variant 행에는 산부인과가 1순위로 있다. 사전·LLM 후보가 성별로 걸러져 남성에게 그 증상이 나오지 않으므로 v1 결과에는 영향이 없다(§11).
  - *(11/17 EF 반영, 독립 검토 I2)* 위 "영향 없음"은 틀렸다: 확인 답 배열만 맞추면(프론트 밖 클라이언트, 답 수정 뒤 남은 값) 남성 + 여성 제한 증상이 확정될 수 있었다. 이제 **확정 증상의 성별 제한과 `filter.sex`(female/male)가 어긋나면 증상 모름**(source `sex_mismatch`)으로 처리하고 warning `symptom_sex_mismatch`(값 없음)를 남긴다. 증상 모름이므로 F2를 묻고 `general`(또는 F2=예 → `injury`)을 추천한다. 성별 모름(unknown)이면 그대로 확정. 이 경우만 DB 함수와 결과가 다르다(전수 대조, §10). 남성 variant 행 자체는 데이터 파이프라인에서 따로 고친다(이번 범위 밖).
- *(11/17 EF 반영, G5)* F2 답은 F2를 묻는 상태(증상이 fallback이거나 모름)일 때만 추천에 쓴다. 증상이 확정돼 F2가 숨겨진 상태라면(variant 행이 없어 fallback으로 가더라도) F2 답을 무시한다.
- **[판단] 증상을 모르는데 아이(T3 child)인 경우**: 확정사항 2.3-5 규칙대로 `general`(내과·가정의학과). 소아청소년과를 넣을지는 팀 확인 대상.
- Supabase SQL 함수를 쓰는 경로가 생기면 나이대 → 정수 나이: child → 10, adult → 40, unknown → null(함수 경계 `<= 18`과 맞춤).

### 8-2. 요약(summary, 템플릿)
- 들어가는 것: 상담 대상(T1), 확정 증상 이름(없으면 "목록에서 찾지 못함"), 그리고 **결과 매핑 slot**에서 `report.onset`(시작), `detail.continuous`·`report.notes`(계속·반복·악화 시점·처치 효과), `detail.worsening`, `detail.pain_score`, 참고할 진료과(최대 3), 답하지 않은 안전 질문이 있으면 그 사실.
- slot 값은 답 code이므로 `applyMappings`가 원래 문항 ID를 함께 보관하고, 요약은 그 문항의 선택지 표시 문구로 바꿔 쓴다(문항 ID를 요약 코드에 박지 않는다).
- 확인하지 않은 정보 줄(항상): "복용 중인 약, 기존 질환, 함께 있는 다른 증상은 확인하지 않았어요. 해당되면 진료 때 꼭 알려 주세요." — v1은 string 문항을 묻지 않으므로(§4-3), 이 정보가 없다는 이유로 가볍다고 단정하지 않게 한다.
- 모두 **선택지 표시 문구와 증상 이름만** 쓴다. 사용자 원문, 질환명, 진단 표현은 넣지 않는다.
- 머리말 "입력한 답을 정리한 참고용 내용이에요. 진단이 아니에요." 꼬리말 "증상이 갑자기 심해지면 119에 연락하세요."
- `summary.ko` ≤ 2000자. `en`은 v1에서 넣지 않는다.
- *(11/16 E 반영)* 경과 줄의 `detail.continuous`·`detail.worsening`은 예/아니요만으로 뜻이 보이지 않아 slot 짧은 이름을 붙인다: `경과: 계속 나타남(예), 점점 심해짐(아니요), 하루 한 번`. 이름표는 `templates.mjs`의 `COURSE_SLOT_LABELS`(slot 키 기준, 문항 ID 아님). 119 정리 요약 줄 이름도 card slot 키 기준(`CARD_SLOT_LABELS`), 매핑 값이 선택지 code가 아니면(`count_1` 등) `DERIVED_VALUE_LABELS`.

### 8-3. 건강정보 후보(profileUpdates)
- 완료 응답에서만 `extractProfileUpdates`를 1번 부른다. **T1 = 본인일 때만.** 아이·다른 사람이면 부르지 않는다(남의 정보가 내 정보로 들어가지 않게, c30 대응).
- 실패하면 빈 배열(응답에서 생략).
- *(11/16 E 반영)* 같은 요청에서 이미 `classifySymptom`을 불렀으면 부르지 않는다(요청당 LLM 1번, `trace.llm.profile.skipped`). 결과 항목은 엔진 계약 검사를 한 번 더 거쳐 맞지 않으면 버린다. `messages`는 프론트가 보낸 배열 그대로 넘긴다(evidence index가 맞도록).

### 8-4. reason=skip
- 1~3단계(안전 규칙, 시작 선택, 키워드)를 그대로 돌린 뒤 남은 문항을 묻지 않고 완료 처리. 안전 규칙에 걸리면 응급 처리가 우선.
- **가장 이른 skip은 Q0를 답한 직후다**(프론트는 답이 1개 이상일 때만 skip 버튼을 보인다, 사실 확인 §3). 이때 N1~N3는 미응답이고, 미응답은 안전 규칙에 걸리지 않으므로 **안전 질문 없이 완료된다.** 그래서:
  - Q0·N1~N3 중 미응답이 하나라도 있으면 요약 **첫 줄**에 "응급 확인 질문에 답하지 않았어요. 의식이 흐리거나 숨쉬기 힘들거나, 갑작스러운 마비·말하기 어려움·심한 가슴 통증·멈추지 않는 출혈이 있으면 지금 119에 연락하세요."를 넣는다(테스트로 강제).
  - 진료과·search는 그대로 준다(BACKEND.md 0.20.0: skip이면 가능한 검색 조건을 돌려주고 부족한 정보를 명시).
  - 다른 선택지: 미응답 안전 질문이 있으면 다음 안전 질문을 followUp으로 함께 보낸다 — §11.
- 증상 확인 전에 skip하면 증상 모름으로 추천한다(§8-1).
- *(11/16 E 반영)* 안전 미응답 문구는 skip뿐 아니라 **모든 완료 응답**에서 검사한다(flow가 `start`·`safety`인 문항 중 보이는 답이 없는 것이 있으면).
  - *(11/17 EF 반영, G6)* 검사 문항은 flow 이름 대신 **답 규칙 조건(`safety_rule_condition`)이 가리키는 문항 전체**로 데이터에서 만든다(`safetyCheckItemIds`, 지금은 Q0·N1·N2·N3 — 테스트로 고정해 시드가 바뀌면 테스트가 깨진다). 문구(N1~N3 내용을 적은 템플릿)는 그대로 둔다. 사전 확인에서 `sym_other`를 고른 뒤 skip하면 LLM을 부르지 않고 증상 모름.

### 8-5. 응답 계약 검사 (`engine/contract.mjs`)
프론트 `normalizeAssistantResponse`와 같은 규칙: 최소 한 필드, followUp(LLM 모듈 `checkFollowUpContract`), `followUp`과 `followUpQuestionId` 동시 금지, search 키 5개만·type·department 일치, emergency 길이, profileUpdates 형식. 테스트에서 `frontend/departments.mjs`를 **읽기만** 해서 search_key가 프론트 목록에 있는지 확인한다.
