# 백엔드 연결 안내

프론트엔드는 Next.js App Router와 React입니다. 실제 LLM endpoint나 로그인, 건강정보 저장 서버는 포함하지 않습니다. 운영시간과 길찾기 API는 기존 Next Route Handler를 사용합니다. 백엔드 담당자는 화면 코드를 수정하지 않고 `care-client.mjs`의 `connectCare`를 브라우저에서 호출해 준비한 요청 함수를 연결할 수 있습니다.

## 연결 위치

`app/medical-app.jsx`에서 기존 `mountMedicalApp`이 완료된 뒤 팀의 연결 함수를 호출합니다. 서버 컴포넌트나 모듈 최상위에서 호출하지 않습니다. 예를 들어 팀이 만든 API 클라이언트를 다음처럼 전달합니다.

```js
import {connectCare} from '../care-client.mjs';

const disconnect = await connectCare({
  requestAssistant: teamAssistantClient,
  rankFacilities: teamRankingClient, // 선택: 검색 결과 추천 순위 연결
  healthNotice: teamReviewedHealthNotice, // 실제 처리 정책에 맞춰 검토한 안내
  questionnaire: teamIntakeQuestions,
  followUpQuestionnaire: teamFollowUpQuestions,
});
// 화면 해제 시 disconnect() 호출. 네트워크 요청 함수는 아래 signal을 사용합니다.
```

위 team 접두사 변수는 백엔드 담당자가 준비할 함수·데이터의 자리 표시자입니다. 아직 실제 서버 주소를 지정하지 않았습니다. `requestAssistant`가 null이면 연결하지 않은 상태로 표시합니다. 초기 문진 데이터는 선택 사항입니다. 전달하면 대화 안에 문진을 표시하며, 문진 내용 교체 시 미제출 답변을 초기화합니다. 이미 제출한 내용은 이전 상담 기록으로 유지합니다.

## 요청 함수

`teamAssistantClient(payload, {signal})`은 Promise로 응답해야 합니다. 프론트엔드의 취소·8초 제한이 적용되므로 실제 fetch에도 같은 signal을 전달합니다. 오류 시 임의 추천을 만들지 않고 재시도 UI를 표시합니다.

| 요청 필드 | 내용 |
| --- | --- |
| reason | message, intake, followup, previousReport |
| locale | ko 또는 en |
| intake | 제출한 질문/선지 스냅샷, 기타 사항, 지역과 completion |
| messages | 사용자가 전송한 문장 배열 |
| followUpAnswers | 준비된 후속 질문에 대한 선택 답변 |
| profile | 직접 입력한 만 나이, 알레르기, 복용약과 병력 |
| search | 지역, 기관 종류, 진료과, 운영 중 필터와 이동수단 |
| previousReport | 선택: 사용자가 확인한 이전 분석서. 아래 0.14.0 계약 참고 |

completion.status는 complete, partial, skipped입니다. complete는 질문 흐름을 끝냈다는 뜻이며, 의학적 정보가 충분하다는 판정이 아닙니다. partial/skipped에는 stoppedQuestionId가 포함됩니다. 미응답 답변은 value:null이며 false 또는 '없음'으로 바꾸지 않습니다. 문진 답변과 대화는 이 페이지의 메모리에만 유지됩니다.

## 응답

```json
{
  "summary": {"ko": "사용자가 입력한 내용을 정리한 문장"},
  "followUpQuestionId": "question-2",
  "search": {
    "region": "춘천",
    "type": "hospital",
    "department": "internal",
    "openOnly": true,
    "mode": "walk"
  }
}
```

각 필드는 선택 사항이며 필요한 필드만 전달합니다. summary는 한국어 ko가 필요하고 en은 선택입니다. summary는 사용자가 확인한 후 분석서 원본에 반영합니다. search는 사용자가 조건 적용 버튼을 눌렀을 때만 실제 조회에 반영합니다. 병원, 운영시간과 거리는 조회된 실제 데이터로 표시하며 응답 문자열로 만들어 내지 않습니다. search에는 위에 나온 필드만 허용합니다.

followUpQuestionId는 followUpQuestionnaire에 등록된 ID여야 합니다. 0.20.0부터는 아래의 followUp 객체로 질문 하나를 직접 전달할 수도 있습니다. 묶음 문진은 미연결 화면용 기존 1~5개 구조를 유지하며, 연결 상태에서는 서버가 응답마다 다음 질문을 결정합니다. 프론트엔드는 질문·선택지 표시와 답변 전달만 수행하고 문진 규칙이나 의학적 판단을 구현하지 않습니다.

질문 형식은 다음과 같습니다. 실제 질문과 선택지는 팀에서 준비합니다.

```json
{
  "id":"intake-1", "version":"v1",
  "questions":[{
    "id":"question-1", "type":"singleChoice", "required":true,
    "label":{"ko":"문진 1"},
    "options":[{"id":"option-1","label":{"ko":"선지 1"}}]
  }]
}
```

## 화면 동작

- 대화가 기본 화면입니다. 문진 시작 또는 질문 데이터 연결 시 대화 안에 선택 문진을 표시합니다.
- 검색 조건 적용 후 대화에 현재 검색 결과의 최대 3개 카드와 전체 결과/지도 열기를 표시합니다. 과거 시점의 검색 결과를 영구 기록하는 방식은 아닙니다.
- 병원 찾기, 분석서, 내 정보는 확장 패널입니다. PC에서는 나란히 보고 작은 화면에서는 패널 하나를 넓게 표시합니다. 닫으면 대화와 미전송 입력이 유지됩니다.
- 대화의 PDF 버튼은 기존 분석서를 열고 인쇄 대화상자를 실행합니다. 서버에 문서를 업로드하거나 병원에 전송하지 않습니다.
- 새 대화는 확인 후 문진, 대화, 분석서와 검색 결과를 비웁니다. 내 정보에 이번 방문 동안 입력한 개인화 정보는 유지합니다.

길찾기 호출 정책 (0.9.2): `/api/route`는 길찾기를 연 기관 1곳과 선택 이동수단에 대해서만 호출합니다. 검색 결과 전체 및 상세정보의 대안 후보에 대한 사전 경로 조회는 하지 않습니다. 유효한 캐시를 재사용하며, 좌표 경로가 제공되면 채팅의 작은 지도에 표시합니다. 응답에 경로 좌표가 없으면 임의의 경로를 생성하지 않습니다.

## 다음 연결 단계 점검 (0.9.3)

- 준비됨: 문진 답변과 스킵 상태, 자유 입력, 추가 질문 답변, 개인화 정보 전달. 요약 확인 후 분석서 반영. 승인된 검색 조건 적용.
- 준비됨 (0.10.0): 실제 검색된 기관 ID를 기준으로 추천 순위와 추천 이유를 전달받아 기존 카드에 표시하는 rankFacilities 응답 형식. 실제 LLM 서버 연결과 추천 판단은 백엔드 담당 작업입니다.
- 준비됨 (0.11.0): 팀이 정한 응급 안내 신호와 외부 영상 ID 표시. 이후: 방문 만족도 Mock UI. 실제 의학적 판단 규칙과 건강정보 저장은 프론트엔드에서 구현하지 않습니다.
- 카드 표시: 상세정보와 경로는 선택한 카드 내부에서 펼치며 펼친 동안 카드 순서를 고정합니다. 검색/상세 클릭으로 경로 API를 호출하지 않습니다.

## 병원 추천 순위 연결 (0.10.0)

`rankFacilities(payload, {signal})`을 `connectCare`에 선택적으로 전달합니다. 생략하면 추천 배지나 이유를 만들지 않고 기존 검색 순서를 유지합니다. 위 예시의 teamRankingClient는 팀이 구현할 함수이며 실제 endpoint는 지정하지 않았습니다.

검색 결과와 운영시간 조회가 끝나면 현재 진료·영업 중인 후보를 한 번 전달합니다. 같은 결과와 문진/대화 조건으로 화면만 다시 그릴 때는 재호출하지 않습니다. 조건, 문진/대화, 후보 또는 운영 상태가 바뀌면 이전 요청을 취소하고 새 후보로 요청합니다. 8초 제한과 오류 후 수동 재시도를 적용합니다.

요청에는 기존 intake, messages, followUpAnswers, profile, search와 함께 아래 candidates가 들어갑니다. reason은 recommendations입니다. 위치 좌표와 전화번호는 후보에 넣지 않습니다. departments는 확보된 진료과만 전달하며 병원명으로 복수 진료과를 추측하지 않습니다. 다음 ID와 추천 이유는 형식 예시입니다. 실행 시에는 payload.candidates의 ID를 사용합니다.

```json
{
  "reason": "recommendations",
  "candidates": {
    "resultSetId": "results-7",
    "items": [{
      "facilityId": "kakao-123",
      "name": "기관명",
      "type": "hospital",
      "department": "internal",
      "departments": ["internal", "family"],
      "status": "open"
    }]
  }
}
```

응답의 resultSetId는 받은 값을 그대로 반환합니다. items의 배열 순서가 추천 순서입니다. reason.ko는 필수(1~240자), reason.en은 선택입니다. 빈 items는 추천 없음으로 처리합니다.

```json
{
  "resultSetId": "results-7",
  "items": [{
    "facilityId": "kakao-123",
    "reason": {"ko": "백엔드가 전달하는 추천 이유"}
  }]
}
```

현재 후보에 없는 ID와 중복 ID는 제외합니다. 후보의 이름, 운영 상태, 운영시간, 거리 등을 이 응답으로 덮어쓰지 않습니다. 다른 결과 묶음이나 이전 문진에 대한 늦은 응답도 적용하지 않습니다. 추천받지 않은 후보는 뒤에 기존 순서대로 표시하며, 표시 시점에도 운영 중인 후보만 카드에 남깁니다. 카드가 펼쳐진 동안에는 사용자가 누른 위치를 유지하기 위해 카드 순서를 고정합니다.

이 연결은 길찾기 API를 호출하지 않으며 이동 거리의 사전 계산도 하지 않습니다. 실패해도 검색 결과와 상세정보/길찾기는 계속 사용할 수 있습니다. 실제 서버 또는 Mock 함수를 연결하지 않은 기본 실행에서는 추천 기능이 동작했다고 표시하지 않습니다.

## 응급 도움 표시 (0.11.0)

별도 응급 판단 API나 의학적 분기 규칙은 추가하지 않았습니다. 기존 requestAssistant 응답에 선택적으로 emergency를 넣으면 해당 입력 맥락의 채팅 안에 표시됩니다. 응급 안내만 반환해도 됩니다. active:false는 백엔드 안내를 해제합니다. 새 대화, 연결 해제 시 해제하며 이전 문진/대화의 안내는 새 맥락에서 표시하지 않습니다. 사용자가 직접 연 응급 도움은 별도로 유지합니다.

```json
{
  "emergency": {
    "active": true,
    "title": {"ko": "팀에서 전달할 안내 제목"},
    "message": {"ko": "팀에서 검수한 안내 문구"},
    "videos": []
  }
}
```

title(최대 120자), message(최대 1000자)는 ko 필수/en 선택 형식이며 필드 자체는 생략 가능합니다. videos는 최대 3개이며, 각 항목은 youtubeId(11자의 영문/숫자/밑줄/하이픈)와 title(ko 필수/en 선택, 최대 120자)입니다. 전체 URL이나 iframe HTML은 받지 않습니다. 팀에서 검수한 영상 ID와 제목을 전달해야 하며, 프론트엔드가 채널이나 의학적 정확성을 자동 인증하지 않습니다. 0.15.0부터 응답에 영상이 없으면 임의의 기본 영상을 자동으로 붙이지 않습니다. topicId에 일치하는 검토된 항목을 선택하거나 사용자가 수동 선택합니다.

119는 고정된 tel:119 링크이며 자동 발신, 자동 신고, 위치 전송을 하지 않습니다. 영상은 사용자가 열 때만 youtube-nocookie.com iframe을 로드하며 자동 재생하지 않습니다. 재생이 제한된 경우에도 유튜브 외부 링크는 사용할 수 있습니다. CSP는 iframe 대상으로 https://www.youtube-nocookie.com만 허용합니다.

현재 위치 확인은 사용자 클릭 시 별도로 GPS 1회 요청 후 카카오 coord2Address로 주소/건물명만 조회합니다. 위치는 세션 메모리에만 두고 문진/추천 payload, 분석서, 브라우저 저장소에는 넣지 않습니다. 병원 검색이나 길찾기를 시작하지 않습니다. 오차가 1km를 넘거나 정확도 정보가 없으면 주소 조회를 생략합니다. 이는 주소 오표시를 줄이기 위한 UI 기준이며, 그 이하 오차에서 실제 위치가 맞음을 보장하지 않습니다. 조회된 주소에 동·호수 등 정보를 추측해 붙이지 않으며 표시된 주소를 실제 위치와 대조하도록 안내합니다.

참고: [소방청 119 구급신고 요령](https://www.nfsa.go.kr/nfa/safetyinfo/emergencyservice/119emergencydeclaration/), [카카오 좌표→주소 문서](https://apis.map.kakao.com/web/documentation/#services_Geocoder_coord2Address), [YouTube 개인정보 보호 강화 모드](https://support.google.com/youtube/answer/171780). 실제 통화, 카카오 주소 조회 및 외부 영상 재생은 키/기기/소유자 설정이 있는 환경에서 별도 확인해야 합니다.

### 응급 위치 선택과 기본 안내 (0.12.0)

외부 지도 검색 버튼 대신 응급 도움 안에서 카카오 지도를 직접 조작합니다. 지도 클릭, 지도 이동 종료, 핀 드래그로 좌표를 선택하고 카카오가 반환한 주소만 표시합니다. 키보드/보조 입력으로는 지도 중심 선택 버튼과 주소 입력을 사용할 수 있습니다. 지도는 사용자가 지도에서 수정을 눌렀을 때만 생성하며 선택 전에는 임의의 좌표를 실제 위치로 확정하지 않습니다.

주소 입력은 두 글자부터 300ms 대기 후 일반 장소(keywordSearch)와 주소(addressSearch)를 함께 조회합니다. 병원·약국으로 검색 범위를 제한하지 않습니다. 후보 선택 시 선택한 주소와 좌표를 같은 지도에 반영합니다. 화살표 키와 Enter로 후보를 선택할 수 있습니다. 단순 직접 입력은 좌표를 추측하지 않으며 이전 선택 좌표를 해제합니다. 실제로 입력한 검색어는 카카오 검색에 사용됩니다.

위치 선택용 지도는 병원 지도와 인스턴스를 공유하지 않습니다. 선택한 응급 위치는 병원 검색 원점, 길찾기 출발지, 분석서, LLM/추천 payload 또는 119로 자동 전달하지 않습니다. 응급 도움을 닫을 때 지도 이벤트와 미완료 검색/주소 조회를 정리하며 선택한 텍스트/좌표는 이번 대화 메모리에만 유지합니다. 새 대화/페이지 새로고침 시 초기화합니다.

응급처치 안내와 영상 영역은 기본 실행에서도 표시합니다. 기본 자료는 emergency-resources.mjs에 분리한 소방청 신고 안내 및 질병관리청 국가손상정보포털의 2023년 교육 영상 「생명을 살리는 심폐소생술 - 119가 도와드려요」입니다. 일반 신고 교육 자료이며 사용자 상황에 맞는 처치를 자동 선택하지 않습니다. 영상 원본을 수정하지 않고 YouTube iframe으로 재생하며 원 출처를 표시합니다. 실제 재생 가능 여부는 외부 소유자/기기 설정에 따라 별도 확인합니다.

상황별 안내는 기존 응답의 emergency.instructions로 검수된 순서를 받을 수 있습니다. 최대 10개이며 각 항목은 ko 필수/en 선택, ko 1~1000자입니다. 0.23.0 React 응급 모달에서는 응답의 instructions/videos를 직접 표시하지 않습니다. topicId와 등록된 emergencyGuides 콘텐츠를 연결합니다. 프론트엔드는 medical triage 규칙이나 의학적 처치 알고리즘을 추가하지 않습니다.

```json
{
  "emergency": {
    "active": true,
    "instructions": [{"ko": "팀에서 검수한 첫 번째 안내"}],
    "videos": []
  }
}
```

## 건강정보 처리 안내 연결 (0.13.0)

문진 시작과 증상 채팅은 같은 상담 안에서 공통 안내를 공유합니다. 입력 전에 별도 체크박스에서 선택하고, 동의하지 않으면 문진·증상 입력을 시작하지 않습니다. 일반 병원 검색·지도 및 수동 응급 도움/119 전화는 계속 사용할 수 있습니다. 내 정보의 건강 항목도 동의 전에는 비활성화합니다.

기본 안내는 외부 문진/추천 API가 연결되지 않은 화면 임시 처리에 대한 **시연용 초안**입니다. 이를 검토가 끝난 실서비스 동의문이나 법적 준수 완료로 간주하지 않습니다. 운영 주체, 실제 처리 목적/항목/기간, 제공업체 및 위탁·제공·국외이전 구조는 팀에서 확정해야 합니다. 필요한 고지와 별도 동의 항목도 그 결과에 맞춰 추가해야 합니다.

실제 adapter 연결 시 connectCare의 healthNotice에 다음 필드를 전달합니다. 아래 값은 자리 표시자이며 실제 정책을 대신하지 않습니다.

```js
const teamReviewedHealthNotice = {
  version: '팀에서 확정할 안내 버전',
  controller: '실제 개인정보 처리 주체',
  purpose: '실제 처리 목적',
  items: ['처리할 건강정보 항목'],
  retention: '우리 서버, 로그 및 제공업체의 실제 처리·보유 기간',
  processing: '실제 제공업체, 처리 방식 및 필요한 이전 안내',
  allowReportImport: true // 안내가 이전 분석서 처리까지 포함할 때만 설정
};
```

외부 assistant 또는 rankFacilities adapter를 연결하고 healthNotice를 제공하지 않으면 동의 버튼과 건강정보 API 전송을 차단합니다. 화면 내부 처리에 동의한 것을 외부 처리에 대한 동의로 재사용하지 않습니다. 안내 내용이나 내부/외부 처리 범위가 바뀌면 이전 확인 상태가 유효하지 않습니다. 이 차단은 React 운영 화면의 클라이언트 보호 장치이며, 팀의 실제 서버에서도 정책과 권한을 검증해야 합니다. 기존 문자열 렌더러는 회귀 테스트용으로만 유지합니다.

확인한 안내 내용의 키와 시각은 페이지 메모리에서만 유지하고 새 대화/새로고침 시 초기화합니다. 동의 증빙을 장기 보관하는 기능은 구현하지 않았으며, 필요한 증빙과 보관 정책은 백엔드 담당자와 별도 확정해야 합니다.

처리 안내에서 동의를 철회하면 문진·대화·분석서와 내 정보 건강 항목을 비우고 미완료 assistant/추천 요청을 취소합니다. 사용자가 이미 내려받은 파일, 복사한 내용 및 이미 외부로 전송된 데이터의 삭제를 보장하는 기능은 아닙니다. 외부 데이터 삭제는 실제 제공업체 정책과 별도 기능으로 처리해야 합니다.

## 이전 분석서 연결 (0.14.0)

PDF는 `pdfjs-dist`로 브라우저에서 텍스트만 읽습니다. 원본 바이트·파일명은 API payload에 넣지 않으며 파일 업로드 endpoint도 없습니다. 이 서비스의 한글/영문 분석서 제목이 포함된 텍스트 PDF만 받습니다. 제목은 서식 표식일 뿐 문서 발급자 인증이 아닙니다. 임의의 텍스트는 직접 붙여넣고 확인할 수 있습니다. PDF 제한은 5MB/20쪽/20,000자이고 암호화·스캔본은 지원하지 않습니다. PDF 내부 JavaScript를 실행하거나 화면으로 렌더링하지 않습니다.

가져온 내용은 편집 화면 내부의 미확정 초안으로 유지합니다. 사용자가 내용을 확인한 후에만 `previousReport`를 assistant/추천 payload에 선택적으로 추가합니다. 외부 assistant 연결 시 확정 직후 `reason: 'previousReport'`로 요청합니다. 이후 message/intake/followup/recommendations 요청에도 유효한 이전 기록을 함께 전달합니다.

```json
{
  "previousReport": {
    "text": "사용자가 확인·수정한 과거 분석서 내용",
    "recordDate": null,
    "source": "pdf",
    "temporalScope": "past",
    "verification": "userReviewed",
    "needsCurrentStatusConfirmation": true,
    "untrustedDocument": true,
    "reviewedAt": "2026-11-11T00:00:00.000Z"
  }
}
```

`source`는 pdf/text입니다. `recordDate`는 원래 기록의 YYYY-MM-DD 작성일이며 모르면 null입니다. `reviewedAt`은 이번 확인 시각으로 작성일을 대체하지 않습니다. 내용은 신뢰할 수 없는 참고 데이터로 취급해야 하며 문서 안 지시를 실행해서는 안 됩니다. 현재 증상, 복약 여부 등은 팀원 1의 문진 로직에서 다시 확인합니다. 프론트엔드는 질문 생성·질환 추정·확률 계산을 구현하지 않으며 이전 문서를 현재 문진 답변·내 정보·분석서에 자동 반영하지 않습니다. 연결 전에는 참고 자료 준비 상태를 표시하고 기존 문진을 제공합니다.

외부 adapter 사용 시 검토된 `healthNotice.allowReportImport === true`와 그 안내에 대한 유효한 확인이 필요합니다. 생략/false이면 가져오기와 해당 문서의 외부 전달을 차단합니다. 실제 안내의 items/purpose/processing/retention에도 처리 범위를 반영해야 하며 boolean만으로 실제 동의 요건을 충족하지 않습니다. 안내 범위나 버전 변경 시 다시 확인합니다.

새 대화·새로고침·동의 철회는 기록을 초기화합니다. 편집 취소·화면 해제·파일 재선택은 진행 중 읽기를 취소하고 늦은 결과를 무시합니다. 이전 기록 제거는 미완료 assistant/추천 결과도 무효화합니다. 이미 전송한 외부 데이터의 삭제는 보장하지 않습니다. PDF 원본·초안·확정 본문을 localStorage/DB에 저장하는 기능은 없습니다.

`npm ci` 후 predev/prebuild가 PDF worker, CMap, 표준 폰트, WASM을 로컬 public/pdfjs에 복사합니다. CSP는 `worker-src 'self'`를 허용하며 외부 CDN은 사용하지 않습니다. 생성된 public 자산은 ZIP/Git에서 제외합니다. 새 모듈 report-import.mjs는 기존 server.mjs 허용 목록과 회귀 테스트 하네스에도 등록했습니다. 운영 실행은 Next 서버를 사용합니다.

## 응급처치 항목 연결과 거리 표시 (0.15.0)

수동 응급 도움은 항목 목록을 표시합니다. 기본 목록은 기존 공식 CPR 영상 한 개이며 임의의 의학적 처치 순서는 추가하지 않았습니다. 팀원 3이 검토한 항목 목록은 connectCare에 다음과 같이 전달합니다. 다음은 형식 예시이며 의학적 콘텐츠가 아닙니다.

```js
connectCare({
  emergencyGuides: [{
    id: 'team-reviewed-topic',
    title: {ko: '검토된 안내 제목', en: 'Reviewed guidance'},
    instructions: [{ko: '팀에서 검토한 안내문'}],
    videos: [{youtubeId: 'Abcdef123_-', title: {ko: '검토된 영상 제목'}}],
    source: {label: '콘텐츠 검토 기관', url: 'https://example.org/reviewed-content'}
  }]
});
```

목록은 0~12개이며 빈 배열은 기본 항목도 숨깁니다. 생략/null과 연결 해제는 기본 목록으로 복원합니다. id는 소문자 영문·숫자·밑줄·하이픈 1~60자이고 중복을 허용하지 않습니다. title은 ko 필수/en 선택입니다. instructions는 최대 10개, videos는 최대 3개이며 적어도 안내 또는 영상 하나가 있어야 합니다. 각각 기존 emergency 정규화와 같은 길이/ID 규칙을 사용합니다. 선택적 source는 label(1~160자)과 HTTPS URL(최대 1000자, 계정정보 없는 URL)로 받습니다. 제목/안내/출처는 텍스트로 표시합니다. 콘텐츠 검토와 갱신은 제공 담당자의 책임이며 URL/ID 형식 검증이 의학적 검증을 의미하지 않습니다.

문진 담당자는 `emergency: {active:true, topicId:'team-reviewed-topic'}`으로 목록 항목을 지목할 수 있습니다. 실제 응답이 instructions/videos를 포함하면 topicId보다 응답 내용을 우선 표시합니다. 알 수 없는 topicId는 기본 CPR 영상으로 대체하지 않고 안내 미연결 상태와 119 접근을 유지합니다. 단순 UI 항목 선택이며 프론트엔드가 증상 키워드로 처치를 추론하지 않습니다. 외부 일반 대화가 해당 콘텐츠를 자동 생성하는 방식으로 사용하지 마세요.

응급 위치 직접 입력을 열기 전에는 검색 후보 요청을 시작하지 않습니다. 지도에서 수정 전에는 지도 인스턴스를 생성하지 않습니다. 지도 닫기/직접 입력 전환/카드 닫기는 지도 리스너를 정리합니다. 위치 직접 입력·후보 선택·좌표 선택은 이번 대화 메모리에만 유지하며, 119/문진 API/병원 검색에 자동 전달하지 않습니다. 모든 위치·영상 상태에서 tel:119 링크를 유지합니다. 영상 iframe은 클릭 후에만 생성하고 자동 재생하지 않으며, 오류 또는 ‘영상이 재생되지 않나요?’ 선택 시 원본 링크를 제공합니다. iframe 내부 오류 전체를 부모가 감지할 수는 없으므로 외부 링크는 항상 표시합니다.

검색 결과의 기본 distance는 사용자 위치와 기관 좌표로 계산한 km 단위 직선거리입니다. 유효한 사용자 위치가 없으면 null입니다. 기본 목록/채팅 거리순 정렬은 이 값만 사용하며 지도 검색 중심으로 사용자 위치를 대체하지 않습니다. 길찾기 후 카드에 표시하는 경로 거리와 기본 정렬 기준을 구분합니다. 가까운 대안 병원의 경로 비교는 기존처럼 유효한 경로 캐시가 있어야 합니다. 어느 표시/정렬 변경도 길찾기 사전 호출을 추가하지 않습니다.

## 서비스 약관·가입 동의와 향후 계정 연결 (0.16.1)

signup-consent.mjs의 `signupConsentPolicy`는 version: signup-policy-1의 서비스 문구입니다. 목적·수집 항목·보유 기간·거부 시 영향을 포함하며 필수 계정 가입 동의와 건강 상담 조건, 선택적 저장을 구분합니다. 이용약관은 6개 조항으로 구성합니다. 운영 주체와 외부 처리 조건이 미등록이므로 operationalReady는 false로 유지합니다. 고객 화면의 동의문을 검토 지시문이나 자리 표시자로 대신하지 않습니다.

`emptySignupChoices`, `changeSignupChoice`, `buildSignupConsentSelection`으로 개별 선택을 관리합니다. healthProcessing 해제 시 healthStorage/reportStorage도 해제합니다. 선택 결과는 아래 형식입니다. persisted:false는 서버 동의 증빙이 아님을 뜻하며 로그인 세션이나 현재 문진의 acceptedKey로 사용할 수 없습니다.

```json
{
  "policyVersion": "signup-policy-1",
  "persisted": false,
  "decisions": [
    {"id": "terms", "agreed": true},
    {"id": "account", "agreed": true},
    {"id": "healthProcessing", "agreed": false},
    {"id": "healthStorage", "agreed": false},
    {"id": "reportStorage", "agreed": false}
  ]
}
```

선택 항목은 기본 해제입니다. 계정 정보는 회원 탈퇴 시까지, 임시 건강정보 처리는 현재 상담 종료 시까지, 선택 저장 항목은 삭제 요청·저장 동의 철회·회원 탈퇴 시까지라는 서비스 조건을 문구로 정의했습니다. 목적 달성/삭제 사유 발생 시 지체 없는 파기를 서버와 백업 정책에서도 충족해야 합니다. 예외 보관이 필요하면 근거·대상·기간을 먼저 확정하고 문구와 실제 동작을 맞춰야 합니다. 채팅 원문과 원본 PDF의 장기 저장은 이 동의 범위에 포함하지 않습니다.

현재 실제 OAuth, 계정 생성, 동의 저장/조회/철회 API는 없습니다. 단일 카카오 진행 버튼은 인증 콜백이 없으면 비활성화되며 가입 성공·서버 저장 완료를 표시하지 않습니다. 팀원 3은 계정별 가입 상태, 정책 버전과 항목별 동의·철회 상태, 저장 설정을 전달해야 합니다. 유효한 같은 범위의 동의는 이후 로그인에서 반복 선택시키지 않는 구조로 연결합니다. 증빙의 계정 연결, 서버 시각, 철회 이력, 사용자별 접근 제한 및 삭제는 서버에서 검증합니다.

운영 주체/문의처, 외부 AI 처리업체와 위탁·제공 관계, 국가/국외이전 조건, 만 14세 미만 정책과 삭제/백업은 연동 전 확정 대상입니다. 현재 외부 AI에 건강정보를 전송하지 않는다는 문구를 표시하며 이를 미래 제공업체에 대한 포괄 동의로 쓰지 않습니다. 업체를 연결할 때 실제 처리 조건에 맞는 안내 및 필요한 별도 동의를 먼저 준비합니다. 운영 주체 등 법적 고지에 필요한 실제 정보를 프론트엔드에서 임의로 만들지 않습니다.

참고: [개인정보 포털 안내](https://www.privacy.go.kr/front/contents/cntntsView.do?contsNo=36), [작성 예시](https://www.privacy.go.kr/front/per/chk/chkComQ11.do), [민감정보 처리](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1034515855).

체크박스는 workspace.css의 health-consent-choice 전용 규칙으로 width/height/min-height/padding을 일반 텍스트 입력과 분리합니다. 행은 18px + minmax(0,1fr)의 grid로 구성하여 가로 스크롤과 세로로 쪼개진 문구를 방지합니다. signup-consent.mjs는 기존 server.mjs 허용 목록에도 포함합니다.

React 운영 화면 상단에는 별도 report 메뉴가 없습니다. 내 정보는 로그인 안내·건강정보·즐겨찾기를 단독 화면으로 제공하며 검색 설정과 Report를 포함하지 않습니다. `navigate('report')`는 내 정보의 내용 확인/PDF에서 별도 report 패널을 엽니다. state.view=report로 기존 인쇄 스타일을 적용합니다. 건강정보는 profile을 기준으로 조회하며 중복 입력하지 않습니다.

state.profile/profileDraft와 state.report.saved/draft는 별개입니다. 영역을 오가거나 입력 내용을 적용할 때 분석서 수정본을 덮어쓰지 않고 기존 원본 변경 알림을 표시합니다. 분석서 직접 편집도 건강정보를 역으로 수정하지 않습니다. 이름/별칭은 React 내 정보 입력에서 제거하고 reportFieldKeys, reportSource, 텍스트/PDF 출력에서 제외합니다. 새 분석서 필드는 age, symptom, onset, allergies, medications, history, notes, questions입니다. 이전 형식 nickname 값은 분석서 정규화/내보내기에서 무시합니다. 기존 profile 모델의 nickname 속성과 문자열 렌더러 입력은 회귀 호환용이며 운영 React는 수집하지 않습니다.

계정/동의 저장 API는 아직 없습니다. 팀원 3은 인증된 계정의 동의 및 저장 설정, 건강정보 조회/수정, 상담별 분석서 조회/저장/삭제 계약을 공급해야 합니다. 현재 폼 적용은 세션 상태 변경이고 저장 체크박스는 기존 지역·정렬 설정의 브라우저 저장만 허용합니다. 회원 건강정보나 과거 분석서가 DB에 저장됐다는 뜻이 아닙니다. 건강정보 반영 후보의 수신·확인 UI는 아래 0.18.0 계약을 사용합니다. 실제 자동 추출과 계정 저장은 아직 연결하지 않았습니다.

목록만은 Explore의 동일 results 배열을 세로 목록으로 표시합니다. 지도는 hidden으로 숨기고 SDK DOM을 보존하여 돌아왔을 때 기존 인스턴스를 재사용합니다. 모드 변경은 display만 바꾸며 liveQueryKey를 바꾸지 않아 검색·경로 사전 요청을 추가하지 않습니다. empty/error/loading 상태도 같은 목록 안에서 표시합니다. 목록 전용 body/list/results의 자연 높이와 overflow를 workspace.css에서 명시해 기존 지도 레이아웃 규칙과 분리합니다. 별도 ES 모듈을 추가하지 않았고 CSP/정적 파일 허용 범위도 변경하지 않았습니다.

## 건강정보 반영 후보 (0.18.0)

기존 `connectCare`의 `requestAssistant` 응답에 선택적 `profileUpdates` 배열을 추가합니다. 후보만 있는 응답도 허용합니다. 프론트엔드는 증상에서 약·질환을 추론하지 않습니다. 서버는 사용자가 실제로 답한 정보만 정리하고, 사용자가 반영할 항목을 확인하도록 해야 합니다.

```json
{
  "profileUpdates": [{
    "id": "medications-1",
    "field": "medications",
    "operation": "set",
    "value": "약 A",
    "evidence": {
      "kind": "message",
      "index": 0,
      "quote": "복용 중인 약 이름은 약 A입니다."
    }
  }]
}
```

예시의 사용자 메시지 배열은 `["복용 중인 약 이름은 약 A입니다."]`입니다. message index는 시스템/안내 메시지를 제외한 사용자 메시지 순서이며 기존 요청의 messages와 같습니다.

| 항목 | 계약 |
| --- | --- |
| 배열 | 최대 4개, id 및 field 중복 금지 |
| id | 영문·숫자로 시작하는 1~64자 영문·숫자·밑줄·하이픈 |
| field | age, allergies, medications, history |
| operation | set 또는 clear |
| value | 최대 500자 문자열. set은 공백만 있는 값 불가, clear는 빈 문자열 |
| age의 set 값 | 0~120 정수의 문자열. 예: "30". 기존 연령대 enum은 거절 |
| evidence.quote | 실제 답변에 포함된 1~500자 문자열 |

근거 종류는 다음과 같습니다. 선택형 문진에서는 질문 문구도 확인 카드에 함께 표시합니다.

| evidence.kind | 식별자 | 확인하는 제출 데이터 |
| --- | --- | --- |
| message | index | 사용자 대화 메시지 text |
| intake | questionId | chat.intakeContext.answers의 해당 답변 |
| intakeNote | 없음 | chat.intakeContext.symptom의 마지막 자유 입력 |
| followup | questionId | assistant.answers의 후속 답변 |

선택 답변의 optionLabel 또는 텍스트 답변 value에 quote가 포함되어야 합니다. 건너뛴 질문·미제출 답변은 근거로 인정하지 않습니다. 이전 PDF만을 근거로 현재 정보를 갱신하지 않고 사용자가 현재 답변에서 확인하게 합니다. 이 검사는 출처 문자열의 일치 검사이며 의학적 정확성 검증은 아닙니다.

독립 문진 모듈은 앱이 준비되고 건강정보 동의가 유효한 상태에서 app.js의 `setHealthUpdateCandidates(items)`를 호출할 수도 있습니다. 동일한 스키마·근거 검증이 적용됩니다. 임의의 운영 샘플이나 시연 버튼은 추가하지 않습니다.

모든 확인 체크박스는 처음에 해제되어 있습니다. 값을 수정하면 해당 항목의 확인도 해제됩니다. 사용자가 선택한 항목만 현재 페이지의 profile/profileDraft에 적용합니다. set은 선택한 필드 전체 교체이며, clear는 미입력으로 비우는 동작입니다. ‘없음’이라는 의학적 답변을 뜻하지 않습니다. 미선택 필드는 유지합니다.

후보 수신 후 상담 입력이 바뀌면 적용을 막습니다. 선택한 필드에 내 정보의 미적용 수정본이 있으면 전체 적용을 거절해 부분 반영을 피합니다. ‘이번 상담에서만 사용’은 원래 제출 답변을 그대로 유지하며 내 정보를 바꾸지 않습니다. 확인 전 후보를 내 정보나 분석서에 자동 반영하거나 별도 건강정보로 전송하지 않습니다.

새 요청·연결 변경·새 대화·동의 철회 시 후보를 초기화합니다. 직접 편집한 분석서 원본과 수정본은 유지합니다. 계정 저장 API 호출이나 브라우저 건강정보 저장은 추가하지 않았습니다. 추후 계정 저장 연결 시 인증·접근 제한·저장 동의·서버 검증은 별도 구현해야 합니다.

## 대화 시작과 API 요청 시점 (0.19.0)

첫 사용자 메시지는 기존 messages에 보관한 뒤 선택형 문진을 엽니다. 초기 메시지 전송이나 분석서 확인만으로 requestAssistant를 호출하지 않습니다. 문진 완료/건너뛰기에서 reason=intake로 현재 메시지, 실제 답변, completion 상태 및 허용된 previousReport를 기존 계약대로 전달합니다. 마지막 자유 입력을 비워도 호출합니다. 제출 이후 추가 채팅은 기존 reason=message를 사용합니다.

분석서 확인은 현재 건강정보나 답변을 덮어쓰지 않고 문진을 엽니다. 첨부 자료의 현재 유효성 확인과 질문 분기는 팀원 1의 담당이며 프론트엔드에 임의의 규칙을 넣지 않습니다. 질문 교체는 setIntakeQuestionnaire 계약을 유지합니다. 동의가 없거나 외부 처리 안내 범위가 바뀌면 기존 API 전송 차단도 유지합니다.

입력창 선택은 동의 UI를 여는 행동일 뿐 네트워크 요청이나 동의 증빙 저장이 아닙니다. 이번 작업은 실제 인증과 즐겨찾기 저장을 포함하지 않습니다. 예정된 즐겨찾기 계약에서는 실제 진료과 일치와 운영시간상 진료 중인 조건을 먼저 확인한 후 해당 후보 안에서 저장 기관을 우선하도록 합의해야 합니다. 이력이나 의료 만족도로 해석하지 않습니다.

## 증상/약국 시작 선택지와 적응형 문진 UI (0.20.0)

기존 requestAssistant 연결과 응답의 search/emergency/profileUpdates 형식은 유지합니다. React 화면에서는 연결된 어댑터가 있을 때 첫 사용자 입력부터 reason=message로 전달합니다. 검토한 분석서는 reason=previousReport로 전달합니다. 이 경로에서는 고정 문진을 선행하지 않습니다. 미연결 상태에는 기존 임시 문진을 사용하며 0.19.0의 요청 시점 설명은 이 미연결 문진 경로에 해당합니다.

시작 선택지는 care-context.mjs의 conversationStarters로 관리합니다. 화면에 보이는 문장을 messages에 그대로 넣고 숨겨진 증상·진단·기간을 추가하지 않습니다. 동의 전에 선택한 항목은 현재 화면에 ID만 대기하며 동의 후 한 번 제출합니다. 취소/거절/새 대화 시 자동 제출하지 않습니다. 시작 문구는 실제 의학적 질문이나 임상 규칙이 아닙니다.

백엔드는 증상 상담과 기관 탐색 의도를 구별해야 합니다. 사용자가 운영 중 약국을 요청했다면 증상을 전제로 병원 진료과 문진을 강제하지 않고, 필요한 지역 등 검색 조건만 확인하거나 pharmacy 검색 조건을 반환합니다. 약 복용·상호작용 관련 질문을 일반 약국 검색과 동일하게 처리하지 않습니다. 이러한 판단은 프론트엔드에서 구현하지 않습니다.

응답에는 기존 followUpQuestionId 또는 다음 followUp 객체 중 하나만 전달합니다.

```json
{
  "followUp": {
    "id": "question-1",
    "type": "singleChoice",
    "required": true,
    "label": {"ko": "문진 1", "en": "Question 1"},
    "options": [
      {"id": "option-1", "label": {"ko": "선지 1", "en": "Option 1"}},
      {"id": "option-2", "label": {"ko": "선지 2", "en": "Option 2"}}
    ]
  }
}
```

질문과 선택지 ID는 1~80자 영문·숫자·밑줄·하이픈, 문구는 ko 필수/en 선택 300자 이하, 선택지는 1~12개이고 ID 중복을 허용하지 않습니다. 직접 전달되는 질문도 이 스키마를 검사합니다. 형식 통과가 의학적 검토를 뜻하지 않으므로 실제 문구와 분류 근거의 승인은 서버가 담당합니다. 프론트엔드는 표시를 위해 임의의 질환명을 생성하지 않습니다.

- 선택 답변은 기존 followUpAnswers에 질문 ID, value(선택지 ID), label과 optionLabel로 전달합니다. reason=followup입니다. 선택지 외 자유 입력은 기존 messages에 들어갑니다.
- 같은 질문 ID의 답변은 교체합니다. 질문을 재확인할 때 식별자 의미가 바뀌지 않도록 서버가 관리해야 합니다.
- 답변 수정은 해당 질문부터 뒤의 답변을 제거하고 이전 질문을 다시 표시합니다. 수정 선택 후 서버가 다음 질문을 재결정합니다. 수정 버튼만으로 요청하지 않습니다.
- 실제 선택 답변이 하나 이상 있으면 ‘여기까지 답하고 찾기’를 제공합니다. reason=skip 요청에 지금까지의 실제 답변만 전달하며 나머지를 false/없음으로 채우지 않습니다. 서버는 미답변을 유지하고 가능한 검색 조건을 반환하거나 부족한 정보를 명시해야 합니다. 긴급 안내가 필요한 경우 기존 emergency 계약을 사용합니다.
- 늦은 응답/입력 변경/동의 변경 방어와 요청 취소·오류 재시도는 기존 처리를 사용합니다. 승인되지 않은 질문 규칙, 실제 LLM 호출, 약국 판단 API는 포함하지 않습니다.
- 약국 search 예: {"type":"pharmacy","department":"pharmacy","openOnly":true}. 실제 조회는 기존 조건 적용 버튼을 사용합니다. 미연결 약국 바로가기만 명시된 해당 조건으로 기존 검색을 바로 실행합니다.

즐겨찾기와 계정별 저장은 다음 작업이며 이번 변경에는 추가하지 않았습니다.

## 패널 크기와 단일 건강정보 입력 (0.21.0)

패널 폭은 React AppView의 도구별 페이지 상태입니다. 서버 API나 개인정보 저장 계약을 추가하지 않습니다. 본문 확대, 상세/길찾기 카드, 검색 조건과 현재 위치 데이터는 기존 상태를 재사용합니다.

React 내 정보에서 건강정보는 profile/profileDraft의 기존 입력을 사용합니다. 상담 편집에서는 age/allergies/medications/history를 별도 입력받지 않습니다. 문서 출력과 복사는 unifiedReportValues를 사용해 저장된 상담 수정본과 적용한 profile의 건강정보를 결합합니다. 기존 문자열 렌더러/분석서 모델은 회귀 호환을 유지하되 React 내 정보의 건강정보 기준 값은 profile입니다. 미적용 profileDraft를 출력하지 않습니다. 증상/메모 수정본은 건강정보 적용으로 덮어쓰지 않습니다.

로그인 진입은 상단 메뉴에서 내 정보로 이동했습니다. 현재는 비회원 상태와 기존 로그인/동의 dialog만 제공하며 실제 로그인 성공이나 계정 저장 완료를 표시하지 않습니다. 팀원 3의 인증 상태/동의/저장 조회 계약은 계속 별도 연결 대상입니다. 화면 폭 상태는 즐겨찾기나 건강정보 처리 동의를 대신하지 않습니다.

## 즐겨찾기 계정 API 연결 (0.22.0)

기본 즐겨찾기는 현재 페이지 메모리에서 동작합니다. 브라우저 저장이나 임의의 로그인 세션/DB를 만들지 않습니다. 아래 독립 연결을 팀원 3이 인증된 HTTP 클라이언트로 제공합니다. 화면의 로그인 문구는 서비스 사용 흐름을 표현하며 실제 계정 생성/저장 완료를 대신하지 않습니다.

```js
import {connectFavorites} from './care-client.mjs';
await connectFavorites({
  list: async ({signal}) => { /* 인증된 목록 조회 후 배열 반환 */ },
  set: async ({facility, favorite}, {signal}) => { /* 성공 응답까지 대기, 실패는 throw */ }
}, {scope: 'opaque-account-scope'});
// 로그아웃/계정 교체 시 먼저 연결을 해제해 이전 계정 데이터를 지웁니다.
await connectFavorites(null, {scope: 'guest'});
```

list는 최대 20개의 기관 레코드를 반환합니다. 각 레코드는 `{id,type,name:{ko,en},address}`입니다. id는 1~128자 영문/숫자/밑줄/콜론/점/하이픈이며 실제 검색 기관의 안정적인 ID와 같아야 합니다. type은 hospital/pharmacy, name.ko는 1~300자, name.en은 선택, address는 500자 이내 문자열입니다. 중복 ID/잘못된 항목은 목록 전체를 거절합니다. 다른 속성은 제외합니다. 환자 건강정보, 방문 이력, 진료 만족도, 운영 상태나 시간표를 저장 계약에 섞지 않습니다.

set에는 추가 시 favorite=true, 해제 시 false와 정규화한 facility를 전달합니다. 서버는 인증된 사용자를 자체 세션에서 식별하고 해당 계정의 항목만 조회/변경해야 합니다. 클라이언트 scope를 권한 증명으로 쓰면 안 됩니다. 멱등 설정 요청으로 구현하고 적절한 타임아웃과 AbortSignal 처리를 제공하세요. UI는 서버 성공 전 목록을 확정하지 않고 실패하면 기존 선택을 유지합니다. 변경 중에는 중복 요청을 막습니다.

계정 연결/해제 시 이전 요청을 취소하고 목록을 즉시 초기화합니다. 이전 scope의 늦은 조회/변경 응답은 무시합니다. 문진 및 추천 API로 전체 즐겨찾기 목록을 추가 전송하지 않습니다. 현재 검색 후보와 ID를 비교해 운영 중 후보 안에서만 즐겨찾기를 우선합니다. 검색 조건/의학적 분류를 즐겨찾기로 덮어쓰지 않습니다.

프로필 목록의 기관을 찾으면 해당 이름/유형으로 기존 검색을 다시 실행합니다. 저장된 주소로 현재 영업 상태를 만들지 않습니다. 상세/길찾기는 새 검색 결과의 기존 기능을 사용합니다. favorites.mjs는 이전 Node 서버 정적 허용 목록에 포함했습니다.

내 정보는 단독 화면이며 상단 언어는 copy의 등록된 번역 키 목록을 사용합니다. 한국어/영어 외 언어의 실제 번역·기관명 표시 리소스는 아직 제공하지 않습니다. 개발 상태 안내를 제품 화면에서 제거했지만 실제 인증/DB/LLM 연결 상태가 바뀐 것은 아닙니다.

## 0.22.1 화면 진입 정리

메인의 open-explore 버튼과 이벤트는 제거했습니다. 지도 검색 진입은 대화 결과의 conversation-map/data-view=explore이며 즐겨찾기 기관의 재검색 기능도 유지합니다. 내 정보의 건강정보 적용·삭제는 검색 조건을 변경하지 않습니다. region/preference 모델과 외부 개인화 검색 인터페이스는 유지하되 내 정보에 설정 UI를 노출하지 않습니다. report는 별도 뷰이며 unifiedReportValues로 최신 적용 건강정보와 상담 수정본을 조합합니다. 실제 로그인·저장 API 계약에는 변경이 없습니다.

## 0.22.2 계정 UI 연결

AccountDialog는 로그인·회원가입을 하나의 흐름으로 표시합니다. 별도의 signup-consent-open 메뉴와 signup-selection-result 중간 단계는 제거했습니다. 입력 동의 정책 자체는 변경하지 않았습니다.

- `needsSignupConsent`: 기본 true. 신규 회원에게 동의 항목을 표시합니다. 인증 담당자는 서버가 확인한 기존 회원이면 false로 지정해 재동의 화면을 생략합니다. 정책 개정 시 필요한 재동의 여부도 서버가 판단합니다.
- `onContinue({intent, consentSelection})`: 필수 동의가 충족된 가입 화면에서는 intent=signup과 buildSignupConsentSelection 결과를 전달합니다. 기존 회원 화면에서는 intent=login, consentSelection=null입니다. 인증/가입 성공을 뜻하지 않으며 OAuth 교환, 사용자 판정, 정책 버전과 동의 기록 검증은 서버 책임입니다.
- onContinue가 없으면 진행 버튼을 비활성화하고 폼을 강제로 submit해도 호출하지 않습니다. 현재 Profile에는 실제 인증 콜백이 연결되지 않았습니다.
- 동의 상태를 페이지에 자동 저장하거나 로그인 성공으로 처리하지 않습니다. 실제 가입 시 저장 동의와 상담 동의를 계정에 기록하고 조회하는 기능은 팀원 3의 연결 범위입니다.
- 건강정보 수집 동의창에서 병원 검색으로 이동하는 우회 버튼만 제거했으며 닫기와 응급 도움 접근은 유지합니다.

## 0.23.0 건강정보 저장·세션·즐겨찾기

건강정보 입력은 profileDraft, 현재 상담과 PDF에 사용할 저장값은 profile로 분리합니다. 폼 입력이나 화면 재렌더만으로 profile을 변경하지 않습니다. 저장 전 상태로 화면을 나갈 때 저장/버리기/계속 작성 모달을 제공하며, 새 대화도 같은 절차를 거칩니다. 실제 계정 저장 API는 연결하지 않았습니다. 현재 ‘건강정보 저장’은 페이지 메모리에서 확정하는 기능이며 DB 저장 성공으로 표시하지 않습니다.

- age는 **만 나이 0~120의 정수 문자열 또는 빈 문자열**입니다. 0은 미입력과 다릅니다. 소수·음수·범위 밖·이전 child/adult/senior enum으로 정확한 나이를 추정하지 않습니다. 기존 enum은 미입력으로 처리합니다. 생년월일은 수집하지 않습니다.
- assistant payload의 profile.age와 profileUpdates.age도 같은 형식을 사용합니다. PDF/복사에서는 만 N세로 표시합니다. 직접 편집한 상담 내용과 저장 전 건강정보는 분리합니다.
- profileConfirmedAt은 현재 페이지에서 마지막 건강정보 확인·저장 시각입니다. 계정 API가 추가되면 특히 age의 확인일을 서버에서 관리하고 다음 상담에서 현재 나이를 재확인해야 합니다. 프론트엔드가 생일을 추정하거나 매년 나이를 임의 증가시키지 않습니다.
- 비회원도 내 정보에서 건강정보 입력하기를 눌러 동일한 민감정보 처리 동의를 시작할 수 있습니다. 기존 동의가 같은 범위/버전으로 유효하면 새 대화에서 반복 요구하지 않습니다. 동의 거절·닫기는 입력 권한을 부여하지 않습니다. 계정 저장 동의는 처리 동의와 별개로 서버 연결 시 확인해야 합니다.
- 새 대화는 문진/대화/분석서/현재 검색/응급 위치를 초기화합니다. 저장한 현재 페이지 건강정보, 즐겨찾기, 유효한 처리 동의와 언어/테마는 유지합니다.
- connectFavorites의 scope가 바뀌면 계정 경계로 취급해 이전 계정·비회원 즐겨찾기를 비우고 건강정보, 미저장 초안, 문진, 대화, 분석서와 동의를 초기화합니다. 응급 위치 요청도 취소해 늦은 결과를 차단합니다. 비회원 목록을 계정에 자동 업로드하지 않습니다. 서버 인증이 확정된 후 계정별 list를 연결하고 로그아웃 시 null/guest로 연결하세요. scope 문자열은 인증 증거가 아닙니다.
- FAVORITES_LIMIT=20을 추가·조회 검증에 공통 사용합니다. 20곳에서도 해제는 가능하며 21번째 추가는 요청 전에 차단합니다. 서버도 사용자별 최대 20개와 기관 ID 중복 금지를 원자적으로 검증해야 합니다. DB는 사용자/기관 ID 관계를 중심으로 저장하고 기관명/주소는 조회용 스냅샷으로만 취급하세요. 과거 운영 상태는 저장하지 않습니다.

## 0.23.0 응급 모달과 콘텐츠

응급 도움은 native dialog로 열립니다. 대화 로그 레이아웃은 유지하며 119 연락을 상단에서 제공하고, 위치 확인/직접 입력/지도 수정은 접힌 위치 영역에서 사용합니다. 로그인이 없어도 열 수 있습니다. LLM을 기다리지 않고 수동 항목 선택과 연락이 가능합니다. 영상이 있는 항목을 선택하면(또는 문진에서 해당 topicId를 반환하면) 영상 플레이어를 카드 안에 표시합니다. 재생은 사용자가 시작합니다.

현재 topicId는 cpr, aed, choking(성인), bleeding, burns(열/뜨거운 물), seizure입니다. 새 영상은 emergencyGuides의 youtubeId로 전달합니다. LLM 응답의 임의 instructions/videos를 직접 렌더하지 않고 등록된 가이드만 사용합니다. 알 수 없는 topicId는 다른 처치로 대체하지 않고 직접 선택하도록 합니다. 문진·LLM의 임상 분류 규칙은 팀원 1, 최종 응급 콘텐츠 검토·관리는 팀원 3의 연결 범위입니다. 소아·영아·임신부 등 범위를 일반 성인 카드로 자동 대체해서는 안 됩니다.

기본 카드의 근거(2026-11-11 열람):
- CPR: 기존 질병관리청 국가손상정보포털 영상 CGG9g1pvJ4g (기존 연결 유지)
- AED: https://www.nhsinform.scot/tests-and-treatments/first-aid/how-to-use-an-aed/
- 성인 기도폐쇄: https://www.redcross.org.uk/first-aid/learn-first-aid/choking
- 출혈: https://www.redcross.org.uk/first-aid/learn-first-aid/bleeding-heavily
- 화상: https://www.nhs.uk/conditions/Burns-and-scalds/
- 경련: https://www.nhs.uk/symptoms/what-to-do-if-someone-has-a-seizure-fit/

영문 자료는 안내 카드를 짧게 번역·요약했고 국내 연락 번호는 119로 표시했습니다. 운영 전 담당자가 국내 적용 범위와 최신성, 번역·영상 내용을 검토해야 합니다. 위 목록은 텍스트 안내의 근거입니다. 기본 영상은 질병관리청(CPR, AED, 성인 기도폐쇄)과 뇌전증지원센터(경련·발작)가 공개한 원본을 사용합니다. 심한 출혈과 열화상에는 행정안전부의 외상환자 응급처치·열화상 영상을 연결하고, 텍스트 참고 자료는 질병관리청 국가건강정보포털의 열상·화상 안내를 제공합니다.

## 외부 AI 업체 미확정 시 연결 기준

현재 OpenAI API를 후보로 검토 중이며 확정된 제공업체가 아닙니다. 공통 ‘외부 AI 서비스 이용’ UI를 먼저 준비할 수 있지만 업체명을 생략한 포괄 동의를 실제 전송 권한으로 취급하지 않습니다. 이 릴리스에는 업체 미확정 상태의 동의 체크박스나 전송을 활성화하지 않았습니다.

실제 연결 전에 팀에서 확정할 데이터:
1. 계약상 제공업체 법인명과 처리위탁/제3자 제공 관계 및 적용 근거
2. 목적과 실제 전송 항목(문진 답변/증상/저장 건강정보 중 필요한 범위), 처리·보관 기간
3. 국외 이전 여부, 국가, 이전받는 자와 연락처, 시점·방법 및 적용 근거
4. 거부권·거부 시 이용 범위, 정책 버전, 동의/고지와 변경 시 재확인 조건

제3자 제공 동의를 근거로 한다면 제공받는 자 등을 명시하고, 처리위탁이면 수탁자와 위탁 업무 공개 등 해당 의무를 적용합니다. 국외 이전은 별도 요건을 검토합니다. 화면에서 일괄적으로 ‘외부 API이므로 제3자 제공 동의 필수’로 단정하지 않습니다. 실제 미확정 정보는 문서에만 남기고 제품에 임의 업체·기간을 채우지 않습니다. connectCare의 healthNotice는 실제 관계가 반영된 안내로 구성하고, 서버에서도 유효한 범위와 버전을 검증해야 합니다. API 키는 서버에서만 관리합니다.

관련 근거: 개인정보 보호법 제17조(제공), 제23조(민감정보), 제26조(위탁), 제28조의8(국외 이전). 전송 업체의 계약과 실제 설정을 확인한 뒤 팀이 최종 처리 방식을 결정합니다.

## 0.23.1 즐겨찾기 조회 분리

- search.origin=favorite로 내 정보에서 시작한 기관 조회를 구분합니다. 이 상태에서는 ConversationResults 및 추천 API 후보 생성을 하지 않고 문진 검색 조건 배너도 표시하지 않습니다. 기존 대화·문진·분석서 자체는 보존합니다.
- criteria.targetFacilityId는 저장한 기관의 안정적인 ID이며 targetQuery는 기관명과 저장 주소의 지역을 조합한 카카오 키워드입니다. 카카오 SDK의 기관 ID 조회 API를 새로 사용하는 것이 아닙니다. 키워드 응답을 ID로 필터링하고, displayedFacilities에도 같은 ID 검증을 적용합니다. liveQueryKey에 target 필드를 포함해 다른 기관·이전 요청 응답이 섞이지 않게 합니다.
- 결과가 있으면 그 기관만 상세정보로 선택하며 route openId는 비웁니다. 운영 필터는 false로 초기화합니다. 영업 종료·미확인 때문에 해당 기관을 숨기지 않습니다. ID가 없으면 기관 정보를 찾지 못했다는 상태를 표시하고 동일 명칭 기관으로 대체하지 않습니다. 다음 페이지가 있으면 기존 더 보기로 확인할 수 있습니다.
- 새 일반 검색·위치 검색·지도 재검색·조건 제거에서는 target 필드를 해제합니다. 기존 채팅 검색은 기존 추천 정책을 사용합니다. favorite 조회 중 자동 대안 기관 탐색도 시작하지 않습니다.
- withCurrentHours는 실 카카오 기관에 schedule이 없으면 status=unknown/hours=null로 정규화합니다. 공공데이터 매칭 실패도 기존 open 상태를 남기지 않습니다. 조회 중이나 실패 시 과거 status를 영업 근거로 사용하지 않습니다.
- 목록·상세·대화의 직선 거리는 facilityDistanceKm를 공통 사용합니다. 출발점은 live.position, 도착점은 현재 결과 기관의 lat/lng입니다. 공급자의 distance 스냅샷이나 지도 center는 직선 거리 근거로 사용하지 않습니다. 위치가 없으면 거리 미확인으로 처리합니다. 정확도 낮은 기기 위치 문제까지 해결했다고 볼 수 없으며 실제 기기 위치 점검은 별개입니다.

회귀 데이터는 가까운 저장 기관과 77km 이상 떨어진 동명 기관을 함께 반환하는 경우, 저장 ID 부재, 운영시간 누락, 실제 종료 시간표, 지도 중심과 기기 위치가 다른 경우를 포함합니다. 기관 조회·상세 선택만으로 경로 API를 호출하지 않습니다. 실 API 키가 없는 모의 환경 검증입니다.

## 0.24.0 인증 상태·로그아웃 연결

현재 프로젝트는 로그인·회원가입 UI를 제공하지만 실제 Kakao OAuth나 세션 서버는 연결하지 않았습니다. 로그인 UI가 있다는 사실만으로 로그인 상태로 판정하지 않습니다. account-session.mjs의 accountId는 서버 검증 결과의 불투명 식별자이며 이름/별칭을 UI에 추가 수집하지 않습니다. 해당 브라우저 모듈을 이전 Node 서버 정적 허용 목록에 추가했습니다.

```js
import {connectAccount} from './care-client.mjs';
const disconnect = await connectAccount({
  getSession: async ({signal}) => {
    // 서버 세션 쿠키로 조회. 아래는 응답 형식이며 고정 로그인 값으로 구현하지 않습니다.
    // 비회원: { authenticated: false }
    // 회원: { authenticated: true, accountId: 'opaque-server-id' }
    return readSessionFromYourServer({signal});
  },
  logout: async ({signal}) => {
    // 서버 세션 무효화. 비정상 HTTP 응답은 throw해야 합니다.
    await endSessionOnYourServer({signal});
  },
  favorites: { list: readFavoritesFromYourServer, set: setFavoriteOnYourServer }
});
```

- app bootstrap에서 매 페이지 로드마다 호출하고 OAuth 완료 후 다시 확인합니다. getSession은 health profile이나 accessToken을 받는 API가 아니며 불필요한 응답 속성을 버립니다. accountId는 비어 있지 않은 최대 120자 문자열입니다. 계정 인증 권한은 서버 쿠키/세션에서 확인하며 클라이언트 accountId/scope를 권한 증명으로 쓰지 않습니다.
- 서버가 인증을 확인한 상태에서만 Profile의 로그아웃 버튼을 표시합니다. getSession 실패는 로그인 완료로 표시하지 않습니다. 요청은 10초 후 취소하고 늦은 이전 계정 응답을 무시합니다.
- 로그아웃은 서버 응답을 기다립니다. 성공 후 비회원으로 전환하며 현재 계정의 건강정보/초안/문진/대화/분석서/즐겨찾기와 응급 위치를 화면에서 제거합니다. 실패하면 기존 상태를 유지하고 오류를 표시합니다. logout 중 중복 요청은 막습니다. 계정 DB 기록 삭제 API를 호출하지 않습니다.
- 어댑터 연결 해제(disconnect)는 현재 화면의 연결을 해제하는 것이며 서버 로그아웃 API를 대신하지 않습니다. 실제 로그아웃에는 logout 성공이 필요합니다.
- favorites가 공급되면 확인된 계정 scope에서 기존 즐겨찾기 API를 사용합니다. 제공하지 않으면 빈 목록이며 계정 저장을 꾸며 표시하지 않습니다. 비회원 목록을 가져오지 않습니다.
- AccountDialog의 OAuth 시작 콜백은 별도 연결 대상입니다. 이 어댑터를 추가했다고 카카오 로그인이 구현된 것은 아닙니다.

## 새로고침 후 데이터 유지 방안(제안)

로그인은 본인 계정을 확인하는 기능이며 건강정보의 저장·복원을 자동 제공하지 않습니다. 실제 DB 조회/저장과 유효한 동의 조회가 필요합니다. 이번 릴리스는 인증 상태 조회·로그아웃 인터페이스를 준비했으며 건강정보 DB 저장/불러오기를 구현하지 않았습니다.

| 데이터 | 회원 새로고침 | 새 대화 | 로그아웃 |
| --- | --- | --- | --- |
| 로그인 세션 | 서버에서 확인해 유지 | 유지 | 서버에서 종료 |

| 저장 동의한 분석서 | 별도 조회 API로 불러오기 | 계정 저장본 유지 | 화면에서 제거 |

비회원 건강정보와 즐겨찾기는 계속 현재 페이지 메모리만 사용합니다. 회원이라는 이유만으로 건강정보나 대화 원문을 localStorage/sessionStorage에 쓰지 않습니다. 건강정보 저장 동의와 실제 저장 확인은 별도로 필요하며 가입 시 거절한 선택 저장을 자동 활성화하지 않습니다. 세션 쿠키는 서버에서 관리하고 브라우저 JS에 인증 토큰을 보관하는 방식으로 대체하지 않습니다. 건강정보 API가 연결되면 저장 버튼은 서버 성공 이후에 확정하고, 조회 시 사용자별 접근 제한/동의 범위/정책 버전을 서버에서 검증해야 합니다. 회원에 한해 새로고침 시 현재 문진·대화를 복원하는 방향입니다. 비회원은 새로고침 시 초기화합니다. 복원 API는 아직 연결하지 않았습니다. 상담 임시 보관의 목적·기간·접근 범위와 API를 팀에서 확정하며, 현 안내의 채팅 원문 비저장 범위를 코드에서 자동 확장하지 않습니다.

## 0.24.1 현재 상담 복원 정책(백엔드 연결 전)

새로고침은 명시적인 상담 종료가 아닙니다. 같은 유효한 현재 상담 세션의 메시지, 답변, 질문 위치, 확인 상태, 분석서 수정본을 복원하는 방향입니다. 새 대화에서만 현재 상담 ID를 종료/교체하고 새 상담을 시작합니다. 계정에 별도로 저장한 건강정보·즐겨찾기·분석서는 유지합니다. 로그아웃은 현재 화면의 개인정보를 비우고 서버의 해당 상담 접근과 세션을 종료해야 합니다.

- 회원과 비회원의 현재 상담 복원을 구분해 설계합니다. 비회원 상담은 새로고침 시 초기화하며 익명 복원 저장을 추가하지 않습니다. 비회원 즐겨찾기는 기존 합의대로 페이지 메모리만 사용하고 계정으로 가져오지 않습니다.
- 실제 연결 전 상담 복원 목적과 임시 보관 기간을 건강정보 처리 안내에 반영하고, 동의 범위와 서버 기록을 맞춰야 합니다. 보관 기한은 현재 임의로 확정하지 않습니다.
- 프론트는 서버가 소유권과 유효기간을 검증한 상담 상태만 복원합니다. 탭별 식별이 필요하면 브라우저에는 불투명한 상담 식별자만 보관하고 원문 건강정보/대화를 localStorage/sessionStorage에 넣는 방식으로 대체하지 않습니다. 익명 세션도 추측 가능한 ID만으로 접근할 수 없어야 합니다.
- 만료·삭제·접근 불가·소유자 변경은 이전 내용을 보여주지 않고 새 상담으로 안내합니다. 로그인 시 비회원 상담을 계정 장기 기록으로 자동 이전하지 않습니다.
- 복원은 화면 상태를 읽는 동작입니다. 마지막 사용자 메시지를 다시 제출하거나 LLM 요청·길찾기 요청을 자동 재실행하지 않습니다. 마지막 응답 완료/처리 중/실패 상태와 메시지·요청 ID를 서버에서 함께 반환하고 중복 전송을 막는 계약이 필요합니다.
- 현재 릴리스에는 실제 상담 저장/복원 API가 없으며 새로고침하면 메모리 입력이 초기화됩니다. 이 절은 구현 완료 주장이 아니라 연결할 정책과 계약입니다.

## 0.24.1 개발 콘솔 로그인

Next development 빌드에서만 dev-console.mjs를 동적 import해 window.medicalDev.login(name='demo')를 제공합니다. 실제 setAccountAdapter/getSession/logout 및 즐겨찾기 연결 경계를 사용하므로 로그인된 UI와 로그아웃 버튼 흐름을 카카오 없이 시험할 수 있습니다. 계정명은 1~32자 영문/숫자/밑줄/하이픈이며 내부 ID는 dev- 접두사를 붙입니다.

모의 계정·즐겨찾기는 설치한 개발 페이지의 메모리에서만 유지합니다. 로그인 성공 메시지는 콘솔에 개발용임을 명시하며 실제 OAuth/DB 요청을 하지 않습니다. 테스트 계정이 달라지면 기존 계정 전환과 동일하게 페이지의 개인정보를 비웁니다. 새로고침하면 모의 계정은 사라집니다. UI의 로그아웃 버튼은 실제 컨트롤러의 서버 응답 대기/계정 비우기 흐름을 따르되 어댑터만 메모리 모의 구현입니다.

process.env.NODE_ENV의 개발 분기에서만 설치하며 production 브라우저에는 medicalDev가 없습니다. 이 모듈은 이전 Node 정적 파일 허용 목록에 추가하지 않았습니다. 실제 인증 우회나 운영용 로그인 수단으로 사용하면 안 됩니다. 소스 코드로 모듈을 가져오는 것과 운영 인증을 얻는 것은 무관하며 운영 API는 서버에서 사용자 권한을 검증해야 합니다.

## 0.25.0 문진 엔진 연결 (/api/care)

- 연결 위치: `app/medical-app.jsx`가 mountMedicalApp 뒤 `connectCare({requestAssistant, rankFacilities, healthNotice})`를 호출합니다. 요청 함수는 `care-adapter.mjs`, 서버는 `app/api/care/route.js`(`lib/care-engine-server.mjs`)입니다. 서버가 `care_engine`의 `runCare`를 Node로 직접 불러옵니다(번들하지 않음). 응답은 엔진 계약 객체만이며 trace·원문은 보내지 않습니다.
- 처리 안내: 원래 화면 안내(`localHealthNotice`, "외부 AI 업체에 제공하지 않습니다")를 그대로 씁니다(영어 화면도 원래 영어 안내). 확인한 뒤에만 요청이 나가고 `consent:{granted:true, version}`이 붙습니다. 서버는 외부 전송을 고지한 안내 버전(`care-openai-1`)일 때만 엔진에 외부 AI 동의를 넘기므로, **지금은 OpenAI를 호출하지 않고 규칙·사전으로만 문진합니다.** OpenAI를 쓰려면 외부 전송을 고지하는 안내(법적 검토)를 그 버전으로 만들어 바꿉니다.
- 미응답 위험 질문: 답하지 않은 `RISK_CONFIRM_<n>`·`SENSITIVE_CHOICE_<n>` ID를 다음 요청 followUpAnswers에 `value:null`로 붙입니다(ID만 페이지 메모리).
- 추천 순위: `rankFacilities`는 `reason:'recommendations'`, `search`, `candidates`만 보냅니다(대화 내용 없음). 후보에 `displayOrder`(현재 목록 위치, 좌표 아님)를 더했습니다. 서버는 LLM 없이 현재 적용한 진료과가 대표 진료과인 곳 → 그 진료과 진료가 확인된 곳 순으로 올리고, 같은 무리 안에서는 displayOrder를 지킵니다. 근거가 없으면 빈 items(기존 순서)입니다.
- 내 정보: 본인 상담이면 만 나이로 문진의 나이 질문(T3)을 대신합니다. 알레르기·복용약·병력은 엔진에 쓰지 않습니다.
- 엔진 데이터: Supabase `ref` 스키마를 10분 캐시로 읽고(검사 통과 시), 실패하면 같은 버전의 시드 CSV로 동작합니다.
