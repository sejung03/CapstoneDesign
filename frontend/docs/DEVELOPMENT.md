# 개발 안내

## 구성과 데이터 경계

Next.js App Router가 HTML, 번들, 정적 자산과 API를 제공합니다. app/medical-app.jsx는 컨트롤러의 renderView 콜백에서 받은 상태를 React에 전달합니다. components/의 JSX 컴포넌트가 문진, 대화, 검색 폼, 병원 카드·상세·운영시간·길찾기, 지도 컨테이너, 분석서와 내 정보를 직접 렌더링합니다.

이번 단계에서는 기존 app.js의 상태와 요청 처리·사용자 동작 로직을 재사용합니다. 모든 상태를 개별 훅이나 별도 스토어로 옮긴 것은 아닙니다. renderView는 flushSync로 화면 갱신을 완료한 뒤 기존 포커스 복원과 지도 갱신이 실행되도록 합니다. 입력 요소는 draft를 캡처한 다음 useLayoutEffect로 동기화하며 입력 노드를 매번 교체하지 않습니다. 전송 직후 입력 초기화와 미전송 입력 유지도 별도로 검증합니다.

React가 화면 마크업을 소유합니다. 지도 SDK는 #kakao-map의 내부, 자동완성은 비어 있는 목록 컨테이너 내부만 관리합니다. 지도 컨테이너는 결과 갱신과 테마 변경 중 유지되며, 화면을 떠날 때 지도와 관찰을 해제합니다. 재사용되는 DOM의 컨트롤러 이벤트는 다음 렌더 전에 해제하고 한 번만 연결합니다. 자동완성 이벤트도 함께 정리합니다. 지번 펼치기와 이미지 실패 처리는 해당 React 컴포넌트의 로컬 상태로 관리합니다.

컨트롤러는 브라우저 useEffect 이후 가져오므로 지도·localStorage·document가 서버 렌더링 중 실행되지 않습니다. Strict Mode와 Fast Refresh의 마운트 해제 시 입력을 캡처한 뒤 위치 관찰, 자동완성, 지도, 타이머, 이벤트와 진행 중 요청을 정리합니다. 기존 문자열 렌더러는 원래 회귀 테스트의 비교 기준으로만 유지합니다. 실제 운영 경로는 renderView를 사용합니다. HTML 삽입은 저장소에 정의된 SVG 도형에만 사용하며, 사용자/API 문자열은 React 텍스트로 표시합니다.

실제 검색 결과를 예시 기관으로 대체하지 않습니다. 테스트만 예시 데이터를 주입합니다. 검색 API에 증상과 건강정보를 보내지 않습니다. 사진, 운영시간, 거리, 접근성을 추정해 채우지 않습니다. Next.js public에는 명시한 자산만 복사합니다. 소스, .env, 테스트, 서버 모듈을 public으로 이동하지 않습니다. 기존 허용 목록 서버는 회귀 테스트에만 사용합니다.

지도, 시간표, 경로 요청은 오래된 응답이 새 검색이나 선택을 덮어쓰지 않도록 처리합니다. 위치와 경로를 localStorage에 저장하지 않습니다. 검색 지역과 정렬 설정 저장은 기본 해제된 체크박스에서 명시적으로 선택합니다. medical-search-settings-v1에는 region과 preference만 저장합니다. 건강정보, 별칭, 연령대, 문진과 대화는 메모리에만 둡니다. 기존 medical-profile-v1은 읽는 즉시 삭제하고 건강정보를 복원하지 않습니다. 예전 검색 설정은 현재 방문에만 적용하며 다시 동의해야 저장합니다.

## 문진에서 검색으로

선택 문진을 N개 진행한 뒤 기타 사항을 자유롭게 입력하고, 전체 답변을 확인합니다. state.intakeStep은 선택 문진(0~N-1), 기타 사항과 선택 지역(N), 답변 확인(N+1)입니다. 상단 진행 표시는 선택 문진, 기타 사항, 내용 확인의 세 구간을 유지합니다. 선택형 화면에는 자유 입력창을 표시하지 않습니다. 마지막 자유 입력과 지역은 선택 사항이며 각각 1,000자, 80자까지입니다.

기본 데이터는 intake-data.mjs의 mockIntakeQuestionnaire입니다. '문진 1', '문진 2'와 '선지 1', '선지 2', '잘 모르겠어요'는 화면 확인용 임시 데이터입니다. 실제 질문과 선지는 문진 담당 팀원이 준비합니다. 프론트엔드는 선지에서 질환, 진료과, 증상 시작 시점이나 추천 순위를 추정하지 않습니다.

향후 API 성공 응답은 app.js의 setIntakeQuestionnaire(payload)에 전달합니다. 현재는 실제 문진 API 요청을 보내지 않습니다. 잘못된 데이터는 TypeError로 거절하며 기존 문진과 입력은 유지합니다. 정상 교체 시 진행 중 답변과 메모를 비우고 첫 단계로 돌아갑니다. 이미 제출한 상담 스냅샷은 그대로 둡니다. 연동 시 첫 표시 전에 응답을 적용하거나 답변 중 교체 여부를 별도로 정해야 합니다. 요청 취소, 재시도와 인증은 API 계약을 정한 뒤 연결합니다.

선택 문진 수는 데이터로 1~5개까지 지정할 수 있으며 현재 임시 데이터는 2개입니다. 마지막 자유 입력과 답변 확인 단계의 위치는 문진 수에 맞춰 자동으로 정합니다. 다중 선택, 조건별 분기와 임상 판단은 구현하지 않습니다.

| 필드 | 계약 |
| --- | --- |
| id, version | 1~80자의 영문, 숫자, 밑줄, 하이픈 |
| questions | 선택 문진 1~5개, 배열 순서로 표시 |
| question | 고유 id, type: singleChoice, label, required, options |
| label | {ko: 문자열, en?: 문자열}, 최대 300자, 영어가 없으면 한국어 사용 |
| options | 1~12개, 각 선지는 id와 label. 선지 ID는 같은 질문 안에서 고유 |
| required | true이면 선지를 선택해야 다음 단계로 진행. 메모 작성으로 대체할 수 없음 |

각 선택은 state.intakeAnswers의 질문 ID에 따라 별도로 보관합니다. 두 문진에서 동일한 선지 ID를 사용해도 서로 덮어쓰지 않습니다. 선택지를 표시한 순서나 문구로 의미를 추측하지 않습니다. 문구와 답변은 HTML로 실행하지 않고 텍스트로 표시합니다.

최종 버튼은 '답변 보내고 병원 찾기'입니다. 정규화한 기타 사항과 지역, 문진별 선택값을 state.chat.intakeContext에 저장하고 검색 화면으로 바로 이동합니다. 대화창을 열고 전달 내용을 표시하며, 검색은 전체 진료과와 거리순으로 시작합니다. 문진 없이 직접 찾기도 유지합니다.

intakeContext는 마지막으로 제출한 답변의 스냅샷입니다. 기존 symptom에는 선택형 답변을 섞지 않고 기타 사항만 담습니다. 선택형 문진이 onset을 임의로 채우지 않습니다. questionnaireId, questionnaireVersion, answers를 함께 전달합니다. answers에는 questionId, type, label, value, optionLabel이 들어갑니다. value는 선지 ID이며 미응답은 null입니다. label과 optionLabel은 제출 당시 한국어/영어 사본으로 이후 질문 데이터 교체의 영향을 받지 않습니다. 재제출 시 스냅샷을 교체하고 chat.messages에는 중복 추가하지 않습니다.

분석서의 '추가로 전할 내용'에는 현재 선택한 질문 원문과 선지 원문을 함께 담습니다. 질문이나 선지 변경도 원본 변경 알림에 반영하고 기존 분석서 수정본은 보존합니다. 마지막 자유 입력도 분석서의 추가 정보에 기타 사항으로 담으며, 주요 증상으로 자동 분류하지 않습니다. 문진과 건강정보는 브라우저 저장소, 검색 API나 URL에 기록하지 않습니다.

검색 상단에는 문진 전달 여부와 실제 정렬 기준을 표시하고 '답변 보기'로 대화창의 입력 내용을 확인할 수 있습니다. 가까운 순서나 API 순서를 LLM 추천 순위로 표시하지 않습니다.

## LLM 추천 연결 시 화면 기준

실제 LLM 응답이나 추천 API는 연결하지 않았습니다. assistant.mjs와 app.js에는 아래 프론트엔드 표시·확인·적용 흐름을 구현했습니다. 추천 순위와 기관별 추천 이유는 아직 표시하지 않습니다. 기존 디자인과 문진, 지도, 검색, 분석서 편집은 유지합니다.

### 연결 방법과 데이터 계약

app.js에서 내보낸 setAssistantAdapter(teamAssistantClient, {questionnaire: teamFollowUpProtocol})로 연결합니다. teamAssistantClient는 실제 백엔드 요청을 담당하는 팀원 구현이며 현재 기본값은 null입니다. 연결하지 않으면 네트워크 요청, 임시 요약, 임시 추천을 만들지 않고 기존 메모와 직접 검색을 제공합니다. setAssistantAdapter(null)로 연결을 해제하면 진행 중 요청도 취소합니다. 호출 예시는 API가 이미 존재한다는 뜻이 아닙니다.

teamFollowUpProtocol은 intake-data.mjs와 같은 id, version, questions 계약으로 전달하는 검토된 추가 질문 목록입니다. 현재 목록 크기는 1~5개입니다. 응답은 그 목록의 question ID만 선택할 수 있습니다. 임의의 새 질문·선지를 생성하여 표시하지 않습니다. 실제 질문 검토와 분기 규칙은 문진 팀원이 담당합니다. 동적 질문 API와 더 큰 질문 목록은 팀의 계약에 맞춰 확장합니다.

클라이언트는 payload와 {signal}을 받으며 Promise로 검증된 데이터를 반환해야 합니다.

| 요청 필드 | 내용 |
| --- | --- |
| reason | message: 대화 자유 입력, intake: 마지막 기타 사항 제출, followup: 추가 질문 선지 선택 |
| locale | 요청 시의 ko 또는 en |
| intake | 마지막 제출 문진 스냅샷. 건너뛰었으면 null |
| messages | 사용자가 보낸 자유 입력 원문 배열 |
| followUpAnswers | 추가 질문 ID, 선택지 ID, 질문과 선택지 문구 |
| profile | 현재 방문의 연령대, 알레르기, 복용 약, 병력. 별칭과 좌표는 제외 |
| search | 현재 지역, 기관 유형, 진료과, 운영 중 조건, 이동 수단 |

선택형 기본 문진과 기타 사항이 빈 제출은 클라이언트를 호출하지 않습니다. 자유 입력 한 번에 클라이언트는 한 번만 호출하고 응답 제한은 8초입니다. followup은 선택형 응답을 질문 엔진에 전달하는 요청입니다. 백엔드는 이를 규칙 엔진으로 처리하며, 선택형 답변마다 추가 LLM을 호출하지 않는 중간보고서 기준을 유지해야 합니다. 프론트엔드는 모델 제공처를 직접 호출하지 않습니다.

응답은 아래 선택 항목 중 하나 이상을 포함합니다. 예시는 계약 설명용이며 서비스에 표시하는 기본 응답이 아닙니다.

~~~json
{
  "summary": {"ko": "사용자 입력에 근거한 상황 정리", "en": "Summary based on the user's input"},
  "followUpQuestionId": "approved-question-id",
  "search": {
    "region": "춘천",
    "type": "hospital",
    "department": "dental",
    "openOnly": true,
    "mode": "traffic"
  }
}
~~~

summary는 2,000자까지의 ko 필수, en 선택 문구입니다. followUpQuestionId는 제공된 질문 목록에 존재해야 합니다. search는 생략 가능하고 region(80자), type(all/hospital/pharmacy), department(departments.mjs의 코드 또는 all), openOnly(boolean), mode(walk/traffic/car)만 지원합니다. 모르는 진료과, 유형 불일치, 시간대나 접근성처럼 미지원 필드가 있으면 응답을 거절하고 오류와 재시도를 표시합니다. 프론트의 형식 검증만으로 의료적 타당성을 보장할 수 없으므로 진단·처방 금지, 근거 확인, 이미 답한 질문 생략과 질문 승인 검증은 백엔드에서 수행해야 합니다.

### 화면 동작

- 상황 요약은 대화창에 표시하고 확인 전에 분석서에 넣지 않습니다. 사용자가 수정·확인한 문구만 '확인한 상황 요약'으로 추가합니다. 편집 취소 시 이전에 확인한 문구를 유지합니다.
- 추가 질문은 등록된 문구와 선지를 표시합니다. 선택한 문구는 대화창과 분석서에 남기고 일반 메시지로 중복 추가하지 않습니다.
- 검색 조건은 적용 버튼을 누를 때만 바꿉니다. 현재 위치를 임의로 생성하지 않으며, 지역을 제안하지 않은 응답은 기존 검색 중심을 유지합니다. 새 지역은 기존 중심보다 우선합니다.
- 검색 적용은 기존 거리순을 사용합니다. LLM 추천순, 추천 배지, 기관별 추천 이유를 만들어 붙이지 않습니다. 길찾기 정보는 기존대로 사용자가 펼칠 때만 표시합니다.
- 대화나 문진이 바뀌면 예전 요약을 새 분석서 원본에 포함하지 않습니다. 검색 조건만 바꾸면 확인한 상황 요약은 유지하되 이전 조건 제안의 적용을 막습니다.
- 실패하면 원문 오류를 노출하지 않고 재시도와 직접 검색을 제공합니다. 오래된 응답, 연결을 교체한 응답과 8초를 넘긴 응답은 적용하지 않습니다. 작성 중인 메시지와 분석서 수정본을 보존합니다.
- 입력과 응답은 메모리에만 두고 localStorage, URL과 콘솔 로그에 남기지 않습니다. 실제 서버를 연결할 때도 요청·오류 로깅과 보관 정책을 별도로 점검해야 합니다.
- 기본 연결 전 상태는 기존 화면과 동일합니다. 개발용 예시 응답과 실패·지연 시나리오는 tests/assistant.test.mjs에서만 주입합니다.

다음 표는 실제 추천 API와 연결할 때 적용할 확장 기준입니다.

| 상태 | 검색과 지도 | 상담과 추천 표시 |
| --- | --- | --- |
| 답변 전달 직후 | 현재 위치나 입력 지역으로 검색을 시작하고 바로 탐색 가능 | 제출한 문진을 보여주며 현재 정렬 기준 유지 |
| 추천 준비 중 | 지도와 목록을 가리지 않음 | 작은 진행 표시, 중복 요청 방지 |
| 추가 정보 필요 | 검색 결과를 유지 | 한 번에 필요한 질문 하나와 짧은 선택지 또는 자유 입력 |
| 추천 도착 | 현재 선택, 지도 위치와 목록 스크롤 유지 | 추천 기준 확인 후 '추천순으로 보기'로 순서 적용 |
| 추천순 적용 | 동일한 기관 ID를 목록과 지도에 사용 | 카드에 추천 표시와 짧은 이유, 지도 마커는 선택 상태와 구별되는 색상 |
| 실패 또는 추천 없음 | 기존 정렬로 계속 탐색 가능 | 재시도 또는 추가 입력, 근거 없는 추천 배지 생성 금지 |

답변 변경, 지역 변경, 직접 정렬은 새 추천과 기존 추천의 상태를 구분할 수 있어야 합니다. 사용자가 바꾼 정렬을 비동기 응답이 강제로 되돌리지 않습니다. 추천 완료만으로 검색 결과를 숨기거나 기관을 자동 선택하지 않습니다. 실제 데이터의 상태와 ID를 받아 표시하며 프론트에서 의료 분류를 만들지 않습니다.

## 분석서

내 정보, 증상과 시작 시점, 사용자 대화를 모아 표시하고 직접 편집할 수 있습니다. 미입력은 명시하며 임상 요약을 자동 생성하지 않습니다. 분석서 편집은 원본과 분리합니다. 원본이 달라져도 저장한 수정본을 덮어쓰지 않고 알림을 표시하며 '원본 다시 반영'으로 갱신합니다.

편집 중 복사와 인쇄는 비활성화하고 저장 후 사용합니다. 인쇄에서는 메뉴와 편집창을 제외하고 긴 내용을 다음 페이지로 이어갑니다. 브라우저의 PDF 저장을 사용합니다. 새로고침 후 복원, 공유 링크와 QR은 아직 구현하지 않았으며, 연결 전 보관 기간과 접근 및 삭제 방식을 정해야 합니다.

## 화면과 문구

메인에는 공통 제목 아래 비슷한 비중의 문진과 챗봇 카드를 놓습니다. PC 너비 비율은 1.05:0.95로 두고 위아래 기준선을 맞춥니다. 문진은 입력과 하단 행동으로 공간을 나누고 챗봇은 대화 영역을 확보합니다. 긴 입력과 작은 높이에서는 영역 안에서 스크롤하며, 모바일에서는 한 열과 자연스러운 스크롤을 사용합니다.

SUIT는 본문, SUITE는 제목에 사용합니다. 폰트는 로컬 제공하며 fonts의 SIL Open Font License를 유지합니다. 화이트와 네이비 테마, 파란 포인트를 쓰고 --line, --line-strong, --section으로 섹션을 구분합니다. 목록과 상세의 병원/약국 SVG에는 접근성 이름을 제공하고 반복되는 설명 문구는 붙이지 않습니다.

문구는 copy.mjs에서 한국어/영어 키를 함께 관리합니다. 버튼은 행동을 짧게 쓰고 불필요한 기술 설명, 중앙점, 예시와 확인 필요 배지는 넣지 않습니다. 아이콘 전용 버튼에는 접근성 이름을 제공합니다. 실제 사진이 있으면 우선하고 없거나 실패하면 SVG를 보여줍니다.

길찾기는 사용자가 눌렀을 때만 상세 정보를 펼칩니다. 일반 카드 클릭은 지도 선택, 상세 보기는 상세 열기입니다. 대화창은 기본으로 열고 사용자가 접은 상태는 화면 이동에도 유지합니다.

디자인 참고: [똑닥](https://ddocdoc.com/), [모두닥](https://www.modoodoc.com/), [Zocdoc 검색 안내](https://www.zocdoc.com/patient-help/en/articles/8975433-how-does-search-work-on-zocdoc), [토스 UX Writing](https://toss.im/tossfeed/article/uxwriter-interview), [SUIT](https://sun.fo/suit/)와 [SUITE](https://sun.fo/suite/). 공개 검색과 서비스 설명에서 행동 중심 문구와 검색 구조를 참고했으며 로그인 후 전체 흐름을 검증한 것은 아닙니다.

## 검증과 남은 작업

npm run check는 모듈 문법, 모델과 DOM 흐름, 서버 HTTP, 키 비노출, 입력 보존, 요청 경합, 시간표 매칭, 경로 동시 요청과 캐시 등을 검사합니다. 실제 브라우저의 픽셀 배치, 실제 API 응답과 위치 정확도, PDF 페이지 구분을 자동 테스트가 대신하지는 않습니다.

남은 작업은 PC/모바일에서 긴 문진과 대화, 지도 선택, 분석서 편집/PDF 확인, LLM 입력과 추천 상태 연결, 운영정보 누락 사례 점검입니다. 공유 링크와 QR 등은 저장과 접근 방식을 정한 뒤 연결합니다.

## 기관 상세 정보

상세 시간표는 한국 시간의 오늘 요일을 블루 색상과 굵기로 강조합니다. 이는 등록 요일 시간표의 강조이며 공휴일 판정이나 휴무 추정을 추가하지 않습니다. 상세 주소는 도로명을 기본으로 한 번만 표시합니다. 명확하게 매칭된 공공데이터 주소가 같은 도로명에 층과 호수를 덧붙인 경우 해당 전체 주소를 사용합니다. 지번은 기본으로 접고 버튼으로 펼칩니다. 제공된 위치 안내도 보존합니다. 층과 호수는 원본에 있을 때만 표시합니다. 주소와 전화번호의 복사는 실제 표시 데이터만 대상으로 하며 클립보드 접근 실패를 안내합니다.

## 진료과와 운영 중 필터

departments.mjs의 공통 목록을 진료과 선택, 카카오 검색어, 기관 카테고리 정규화, 명시적 대화 조건에 사용합니다. 카카오 분류와 키워드 기반 검색이며 기관의 전체 진료과 목록이나 전문의 자격을 확정하는 자료가 아닙니다. 공공데이터 QD 코드와의 연결은 별도 매핑이 필요합니다.

'운영 중인 곳'을 선택한 검색은 입력어가 비어 있어도 기존 검색 지역, 기존 검색 중심, 현재 위치, 지도 중심 순서로 범위를 찾습니다. 범위가 없으면 위치를 요청하고 실패 시 기존 위치 오류 안내를 사용합니다. 직접 입력한 검색어가 있으면 우선합니다. 운영 상태 판정과 운영정보 누락 처리 정책은 바꾸지 않습니다.

운영시간을 찾지 못했거나 시간표가 모두 비어 있으면 등록시간 안내를 표시하지 않습니다. 상세 안내는 병원의 진료시간과 약국의 영업시간을 구분합니다.

운영 중 배지는 병원과 약국 모두 파란색으로 표시합니다. 병원 SVG와 기본 지도 마커는 청회색, 약국은 기존 초록색을 유지합니다. 선택 마커의 주황색은 선택 상태 구분용으로 유지합니다. 배지의 점멸 효과는 점에만 적용하며 동작 줄이기 설정에서는 끕니다.

## 가까운 대안 병원과 검색어 후보

상세에서 같은 진료과의 더 가까운 병원을 최대 3곳 표시합니다. 일반 병원명 검색은 결과가 한 곳뿐일 수 있으므로, 상세 진입 시 확인된 진료과와 사용자 위치로 주변 기관을 별도 조회합니다. 첫 페이지의 최대 15곳을 비교하며 전체 지역의 모든 병원을 탐색한 결과나 LLM 추천 순위가 아닙니다.

- 별도 후보는 state.discovery에 보관합니다. 원래 검색 결과를 교체하지 않습니다. 후보를 선택한 동안만 해당 기관을 상세와 지도에 포함하고, 상세를 닫으면 원래 검색 결과로 돌아갑니다.
- 기관 ID로 중복을 제거하고 병원만 비교합니다. 기준 병원보다 사용자 위치에서의 경로 거리가 짧아야 합니다. 동일한 이동 수단과 현재 위치에 해당하는 유효한 경로 캐시만 사용합니다. 거리 미조회·실패·만료 시 직선거리로 대체하지 않습니다.
- 검색 시작 시각 live.searchedAt을 기록합니다. 후보는 검색 시작 시각과 표시 시각에 모두 등록시간상 운영 중이어야 합니다. 시간표 누락·불명확·기한 초과 상태나 조회 오류가 있으면 제외합니다. 기존 등록 요일 시간표 판정을 재사용하며 휴일 정책을 새로 추정하지 않습니다. 화면에도 등록시간 기준임을 표시합니다.
- 알려진 departments 배열과 기존 대표 department를 활용합니다. 복수 진료과인 기준 병원은 현재 검색에서 명시한 진료과를 사용하고, 진료과 기준이 없으면 임의로 하나를 골라 비교하지 않습니다. 카카오 대표 카테고리가 기관의 전체 진료과를 뜻하지 않으므로 전체 진료과 검색에는 백엔드의 기관 데이터 연결이 필요합니다.
- 진료과·위치·운영시간·경로 정보가 없으면 이유를 표시합니다. 조회 중, 실패·재시도, 비교 가능한 후보 없음도 구별합니다. 운영시간과 거리 조건을 완화해 결과를 만들어내지 않습니다.
- 다른 검색 조건의 이전 결과는 대안 추천에 사용하지 않습니다. 상세를 닫거나 검색을 바꾸면 늦은 조회 응답은 폐기합니다. 후보를 눌러도 길찾기 패널은 자동으로 펼치지 않습니다.
- 주변 후보 조회는 카카오 장소 검색과 기존 공공데이터 운영시간 조회를 사용합니다. 이미 있는 시간표와 경로는 재사용하고 새 경로도 기존 최대 2개 동시 요청 제한과 캐시를 공유합니다.

검색창 아래에는 최대 6개의 입력 후보를 표시합니다. 진료과 목록의 이름·별칭과 이미 조회한 기관에 더해, 두 글자 이상 입력하고 300ms 동안 추가 입력이 없으면 입력한 이름을 카카오 키워드 검색으로 조회합니다. 병원과 약국 카테고리를 각각 조회하며, 현재 위치는 정렬 기준으로 사용하고 반경을 제한하지 않아 명시한 다른 지역을 막지 않습니다. 인기 검색어나 비공개 자동완성 API를 사용하지 않습니다.

- 한글 조합 중에도 화면 후보를 갱신합니다. 조합 중 Enter는 후보 선택으로 가로채지 않습니다. 삭제나 공백으로 마지막 글자를 확정해야만 목록이 나오는 흐름을 피합니다.
- 요청은 입력별로 지연하고 같은 위치·검색어 결과를 최대 20개, 30초 동안 현재 방문의 메모리에 캐시합니다. 최근 검색 기록을 localStorage에 저장하지 않습니다. 문진이나 대화 원문을 검색어로 자동 전달하지 않습니다.
- 새 입력·Escape·화면 이동 후 이전 응답은 목록을 덮어쓰거나 다시 열지 않습니다. 조회 중·실패·후보 없음도 표시하며 직접 검색은 계속 사용할 수 있습니다.
- 후보 갱신은 텍스트 노드로 처리하고 지도를 다시 그리지 않습니다. 방향키·Enter·Escape와 포인터 선택을 지원합니다.
- 후보 선택은 검색 입력과 필터를 채운 뒤 기존 검색 폼을 requestSubmit으로 즉시 제출합니다. 포인터 선택과 방향키 후 Enter 선택 모두 한 번만 검색하며, 선택 직후 검색창의 프로그램 포커스 때문에 후보가 다시 열리지 않도록 처리합니다. 기관명을 고르면 기관 유형을 맞추고 이전 진료과 필터를 해제합니다. 진료과 후보를 골랐는데 지역 입력이 비어 있으면 기존 범위 또는 실제 위치를 이용합니다. 임의의 위치를 넣지 않습니다.

크기 변경은 React 표현 상태만 변경합니다. app.js의 검색/경로/지도 mount를 호출하지 않습니다. 기존 kakao-client.mjs ResizeObserver가 지도의 중심을 유지하며 relayout합니다. 검색 패널은 컨테이너 너비에 따라 조건 행과 목록/지도 배치를 조정합니다. 키보드·드래그·취소·확대·복원·패널별 비율 보존과 추가 API/지도 생성 없음을 React 번들 테스트로 확인합니다.

Profile이 기존 AccountDialog를 보유하며 Header의 로그인 버튼은 제거했습니다. Report의 embedded 모드에서 건강정보 필드는 화면/편집에 중복 표시하지 않고 출력 전용으로 유지합니다. 인쇄에서는 해당 필드를 다시 표시하고 페이지 제목/계정/프로필 폼은 숨깁니다. unifiedReportValues로 최신 적용 건강정보와 상담 수정본을 결합하므로 복사와 PDF의 값이 일치합니다. 일반 보고서 모델/문자열 렌더러 테스트는 유지합니다.

검증은 단위 233개 + Next/React 23개와 프로덕션 빌드입니다. jsdom과 모의 SDK/API를 사용했으며 실제 외부 연동이나 PC/모바일 시각 검증을 완료했다는 의미는 아닙니다. 새 의존성/ES 정적 모듈/CSP 변경은 없습니다.

## 0.24.1 개발 콘솔 시험

개발 UI 통합 시험은 jsdom에서 빠져 있는 Web Streams API를 Node 런타임으로 제공하고, Turbopack 비동기 모듈 평가 시 currentScript를 보완합니다. 이는 시험 환경 보완이며 제품 코드는 변경하지 않습니다. 실제 브라우저 육안 검증을 대신하지 않습니다.
